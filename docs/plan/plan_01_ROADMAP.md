## 1. analysis-service — 소화기 AI 판독 (1순위)

### 목적

점검 사진에서 **소화기가 지정 위치에 비치되어 있는지**를 AI 가 1차 판독한다. 사람은 그 결과를 확인하거나 고친다.

현재 analysis-service 는 사진 **품질**(관심 영역의 밝기 · 선명도 → `OK` / `RETAKE`)만 본다. 사진 **내용**(소화기가 있는지)은 사람이 판정 화면에서 입력한다. 이 항목은 그 내용 판독을 AI 로 넓히는 첫 단계다.

### 구현 가능 여부: 가능

지금 구조 그대로 붙일 수 있다.

- **작업 큐:** analysis-service 의 작업 큐(LISTEN/NOTIFY + `FOR UPDATE SKIP LOCKED`)가 사진마다 한 번씩 분석을 돌린다. 품질 검사 뒤에 판독 단계를 하나 더하면 된다.
- **사진과 결과의 흐름:** 사진은 inspection-service 에서 받아 오고, 결과도 inspection-service 로 돌려보낸다. 기존 경로를 그대로 쓴다.
- **기술:** Python 서비스이므로 학습 모델(YOLO 계열, PyTorch/ONNX)을 그대로 쓸 수 있다. 사진 한 장 추론은 CPU 로도 처리할 수 있는 수준이다.
- **도착 정확도:** 로봇은 점검 지점에 위치 오차 0.12m · 방향 오차 0.15rad 안으로 도착한다. 같은 지점의 사진 구도가 거의 같으므로 "사진 속 기대 영역"으로 위치를 판단할 수 있다.

### 방식: 물체는 학습하고, 위치는 설정한다

모델은 **"소화기라는 물체"**를 찾도록 학습한다. **"지정 위치인가"**는 학습하지 않고, 지점 설정값과 판정 규칙으로 정한다.

- **이렇게 나누는 이유:** 지정 위치 사진만으로 학습하면 모델이 소화기가 아니라 그 자리의 벽과 배경을 외운다. 그러면 조명이나 각도가 바뀌거나 다른 현장에 가면 틀리고, 지점이 늘 때마다 다시 학습해야 한다.

| 구분 | 내용 | 정하는 방법 |
| --- | --- | --- |
| 학습 (모델) | 사진 속 소화기를 찾는다: 사각형 위치 + 확신도 | 객체 인식 모델(YOLO 계열)을 소화기 사진으로 미세조정 |
| 설정 (지점) | 이 지점 사진에서 소화기가 있어야 할 영역 | 관리자가 기준 사진에서 영역을 지정해 지점마다 저장 |
| 판정 규칙 (코드) | 위 둘을 맞춰 결론을 낸다 | 아래 표 |

판정 규칙:

| 판정 | 조건 |
| --- | --- |
| 비치됨 | 소화기가 기대 영역 안에서 확신도 기준 이상으로 보임 |
| 위치 이탈 | 소화기는 보이지만 기대 영역 밖에 있음 |
| 미비치 | 소화기가 보이지 않음 |
| 판독 불가 | 사진이 어둡거나 흐림. 기존 품질 검사의 `RETAKE` 가 이 역할을 한다 |

기대 영역에는 도착 오차만큼 여유를 둔다.

**사람 최종 확인:** 안전 점검이므로 AI 는 1차 판독만 한다.
- 판정 이력에는 AI 결과(판정 · 확신도 · 사각형 · 모델 버전)와 사람 결정을 따로 남긴다.
- 지금처럼 사람 판정은 덮어쓰지 않고 쌓는다.

### 학습 데이터

1. **공개 데이터셋으로 시작:** Roboflow Universe 등에 소화기 라벨이 달린 데이터셋이 있다.
2. **현장 사진 추가:** 로봇이 각 지점에서 거리와 각도를 조금씩 바꿔 찍은 사진, 그리고 실제 현장 사진을 더한다.
3. **빈 자리 사진 포함:** 소화기를 치운 상태도 찍어 "미비치"를 구분하게 한다.
4. **라벨링:** 사진마다 소화기 위치를 사각형으로 표시한다. 처음에는 수백 장 수준으로 시작하고, 오판 사례를 보며 늘린다.
5. **평가:** 학습에 쓰지 않은 현장 사진으로 검증한다. 미비치를 비치됨으로 잘못 보는 비율을 가장 중요하게 본다.

### 서비스별 변경

| 서비스 | 변경 |
| --- | --- |
| analysis-service | 모델 파일 로드, 품질 검사 뒤 소화기 인식 → 판정 규칙 적용. 결과(판정 · 확신도 · 사각형 · 모델 버전)를 inspection-service 로 보냄 |
| inspection-service | 지점에 "점검 항목(소화기 비치)"과 "기대 영역" 추가(Flyway 마이그레이션). AI 판독 결과 저장(`observation_analysis` 확장 또는 별도 테이블) |
| 화면 | 관리자: 지점 기준 사진 위에 기대 영역 지정. 사용자: 사진 위에 찾은 사각형과 기대 영역을 겹쳐 보여 주고, AI 판정을 "확인 / 수정" |
| 시뮬레이션 | 월드의 소화기(빨간 상자 `target_red`)를 실제 모양의 소화기 3D 모델로 교체 — 실제 소화기로 학습한 모델은 빨간 상자를 알아보지 못한다 |

### 단계

1. 공개 데이터셋 + 라벨링으로 소화기 인식 모델 미세조정, 정확도 확인
2. 시뮬레이션 소화기를 3D 모델로 교체, 로봇 촬영 사진 수집
3. 지점에 점검 항목 · 기대 영역 추가(DB · 관리자 화면)
4. analysis-service 에 추론 · 판정 규칙 추가, 결과 저장
5. 사용자 화면에 판독 결과 표시와 사람 확인 · 수정
6. E2E 시험: 비치됨 · 위치 이탈 · 미비치(소화기를 치운 월드)를 각각 확인

### 완료 기준

- P1 점검에서 소화기가 있으면 "비치됨", 치우면 "미비치", 옮기면 "위치 이탈"이 나온다.
- 화면에 근거(찾은 사각형 · 확신도)가 보이고, 사람이 확인하거나 고칠 수 있다.
- analysis-service 가 멈춰도 점검 · 사람 판정 흐름은 막히지 않는다(지금과 같음).

## 2. 주행 제어기 개선 (별도 작업, 시나리오 구현과 분리)

시나리오 구현(`feat/scenarios-sim`)에 포함하지 않는다. 이후 별도 작업으로 한다.

> **진행(2026-11-18, 브랜치 `feat/drive-controller`, 시뮬레이션):** 제어기를 Regulated Pure Pursuit 에서 MPPI 로 바꿨다.
> 기준은 "감속 없이 최대 속도로 달리는 시간의 비율"로 잡았다. 측정값과 시험 방법은 `docs/guide/guide_02_RUNNING.md`, 바꾼 값 · 버린 시도 · 이유는 `nav2_params.yaml` 머리 5).
> - 원인: 좁은 곳에서 느려지거나 끊긴 것은 계획 쪽이 아니라 제어 쪽이었다(RPP 의 비용 · 곡률 감속과 충돌 예측 정지).
> - 결과: 이 시설의 경로(직선 · 굽은 길 · 점검 지점)에서 최대속도 유지 50~77% → 84~95%. 폭 0.7m 틈까지는 속도를 유지한다.
> - 한계: 폭 0.6m 틈은 MPPI 가 멈칫하거나 실패한다(RPP 는 느리게 지났다). 달리는 중 갑자기 놓인 팔레트(남는 폭 0.65m)도 같은 이유로 느리다.
>   로봇을 원 0.22m 로 보는 한 남는 문제이고, 제어기만 실제 외곽으로 보게 하면 0.9m 문에서 벽에 끼었다. 계획 · 제어 양쪽을 함께 외곽으로 바꾸는 것은 해 보지 않았다.
> - 계획(2026-11-18~19): 계획기 Smac 2D A\* → Theta\*(직선 + 모퉁이), 처음 계획을 유지하는 행동 트리, 제어기용 비용 지도 0.05 → 0.025m
>   (폭 0.6m 틈을 속도를 유지하며 통과), 목표 브리지의 몸통 채우기 · 물러나 자세 잡기 · 두 번 막힌 자리 막기.
>   장애물 시험은 달리는 도중 계획 경로 위에 놓는 여섯 시나리오로 다시 짰다(38개 확인 통과). 자세한 내용은 `docs/guide/guide_02_RUNNING.md` "계획 방식과 좁은 틈".
> - 남은 일: 실기(Raspberry Pi 4, Cortex-A72 4코어, ROS 2 Jazzy · Nav2 미설치)에서 제어 주기 10Hz 를 지키는지 재야 한다. 못 지키면 `batch_size` · `time_steps` 를 줄인다.
>   Jazzy 는 MPPI 파라미터 이름 · 기본값이 Humble 과 달라 설정을 옮겨야 한다.

### 문제

지금 주행 설정으로는 **좁은 골목 같은 곳을 로봇이 통과하지 못하는 일**이 있다.

### 요구

1. **A\* 로 전체 주행 계획을 세운다.**
2. **제어기가 그 A\* 계획을 따라 주행한다.**
3. **제어기가 계획을 따라가면서, 주행 중 새로 생긴 장애물을 실시간으로 피한다.**

### 지금 구성과의 차이

| | 지금 | 요구 |
| --- | --- | --- |
| 전체 계획 | Smac 2D A\* (+ smoother) — 요구 1 은 이미 충족 | 그대로 |
| 제어기 | Regulated Pure Pursuit — 받은 경로를 그대로 따라간다. 앞이 막히면 느려지거나 멈출 뿐 **옆으로 피하지 않는다** | 경로를 따라가되 스스로 피하는 제어기 |
| 새 장애물 대응 | 비용 지도에 찍힌 뒤 **경로를 다시 계획**해서 돌아간다(계획 층에서 처리) | 제어기가 실시간으로 피한다(제어 층에서 처리). 크게 돌아가야 하면 지금처럼 다시 계획 |

### 작업을 시작할 때 볼 것

- **좁은 곳을 못 지나는 원인부터 가른다.** 후보: 팽창 반경 · 비용 기울기(지금 0.6 / 3.0)로 통로가 "비싸게" 보여 계획이 안 나오는 것, 로봇 외곽(footprint) 여유, 제어기가 충돌 예측으로 멈추는 것, 위치 추정 오차. 원인에 따라 고칠 곳이 계획 쪽일 수도 제어 쪽일 수도 있다. `drive_probe.py` 로 통로 폭별 통과 여부를 먼저 잰다.
- **제어기 후보:** 경로를 따르면서 장애물을 피하는 Nav2 제어기는 MPPI, DWB 가 있다. 좁은 통로 통과와 회피를 함께 보면 MPPI 가 1순위 후보다. 다만 연산량이 커서 지금 시뮬레이션 환경(Apple Silicon 에서 amd64 에뮬레이션)과 터틀봇의 Raspberry Pi 에서 주기를 지키는지 확인해야 한다.
- **바뀌는 범위:** 로봇 쪽 Nav2 설정(`ros/sim/src/config/nav2_params.yaml`, 파일 머리의 변경 목록도 함께)뿐이다. 서버와의 목표 계약(`/inspection/goal`)은 그대로라 서비스 · 화면은 바뀌지 않는다. 브리지의 `detoured`(우회) 판단은 "계획 길이 대비 주행 거리"라 제어기가 피해 간 경우도 잡힌다.
- **확인:** 기존 전 구간 시험의 장애물 시나리오(우회 · 다른 길 · 진입 불가)가 그대로 통과해야 하고, 좁은 통로 통과 시험을 더한다.
