# 시나리오 수정 계획: 소화액 투척 · 소방 관제

준비 중인 두 시나리오를 지금 구조에 올리려면 무엇을 더하고 고쳐야 하는지 정리한다.
주고받는 모양(토픽 · API · DB 표 · 상태 흐름)은 [INTERFACES.md](INTERFACES.md) 에서 정한다 — **계획 단계는 그 상세 설계까지가 완료다.**
현재 구조는 [guide/RUNNING.md](../guide/RUNNING.md), 소화기 인식 모델의 학습 방식은 [ROADMAP.md](../plan/ROADMAP.md) 를 본다.

| | 시나리오 1: 소화액 투척 | 시나리오 2: 소방 관제 |
| --- | --- | --- |
| 성격 | 화재 **대응** (사건 하나를 끝까지 처리) | 화재 **예방** (정해진 상태에서 벗어나면 알림) |
| 흐름 | 젯봇 순찰 → 열화상 이미지로 초기 화재 판독 → 터틀봇 호출 → 이동 → 투척 | 터틀봇 · 젯봇 순회 점검 → 그 위치에서 찍은 사진 판독 → 정상 · 경고 · 비상 분류 → 관제 알림 |
| 지금 구조와의 거리 | 멀다: 젯봇 연결 · 위치 추정, 사건 처리, 투척 명령이 새로 필요 | 가깝다: 점검 · 촬영 · 분석 · 예약 · 대시보드 경로가 이미 있다 |
| 순서 | 2번째 | 1번째 |

## 0. 정해진 것

| 항목 | 결정 |
| --- | --- |
| 구현 범위 | **실물 디바이스 두 대(터틀봇 · 젯봇)를 뺀 전부를 구현한다.** 투척 기구는 터틀봇에 달리는 실물 디바이스이고, 투척할지의 **판단은 서버가 한다.** 투척 인터페이스는 설계 목록에 넣어 구현한다 |
| 계획 단계의 완료 | 인터페이스 상세 설계까지([INTERFACES.md](INTERFACES.md)). 그 전에는 구현하지 않는다 |
| 미정 항목 · 실측 | 미정 항목은 인터페이스(설정 자리)를 마련해 두고 대응한다. 카메라 판독은 analysis-service 의 판독 인터페이스 하나로 받는다. 실측은 구현 후 작업이다 (5절) |
| 투척을 누가 시작하나 | **두 모드를 모두 만든다**: 사람 승인 모드 / 자동 투척 모드 (4.5) |
| 젯봇 위치 | **카메라 2대(같은 방향을 보는 스테레오)로 위치를 찾고, 터틀봇과 같은 지도를 쓴다.** 대기 구역 1곳의 ArUco 마커 하나로 작업(순찰 계획) 시작 전 · 종료 후에 정렬한다. 오차가 크면 정렬 구역 1~2곳 추가 (4.1) |
| 시연용 초기 화재 | **열화상 카메라 출력 이미지를 인쇄해 시연 공간에 둔다.** 그 이미지를 보고 화재 여부를 판독한다. 현업에서는 실제 열화상 카메라 영상이 그 자리에 들어간다 (4.2) |
| 젯봇 기반 작업 | **별개 항목이다(다른 담당자가 진행 중).** 공개된 젯봇 코드(ROS 1)를 ROS 2 로 옮기고 스테레오 카메라 설정으로 동작하게 한다. 이 문서의 작업은 그 결과물 위에 올린다 (4.0) |
| 소방 관제를 하는 로봇 | **터틀봇과 젯봇 둘 다 구현한다** (2절 "두 로봇") |
| ROS 2 배포판 | **젯봇 · 터틀봇 · 브리지 노드를 한 배포판으로 맞춘다. Jazzy(실제 터틀봇과 같은 판).** Humble 에서 옮겼고 노드 · 토픽 구성과 서비스는 그대로다 (3.4) |
| "멀티 시나리오"의 뜻 | **점검 규칙이 여러 종류**(소화기 위치, 계기판 등). 그 위치에서 찍은 사진으로 **정상 · 경고 · 비상** 등급을 매긴다 (2절) |

## 2. 시나리오 2: 소방 관제 (먼저 한다)

### 흐름

1. 예약 점검이 로봇(터틀봇 또는 젯봇)을 지점으로 보낸다(터틀봇은 지금과 같음).
2. 도착해 사진을 찍는다(지금과 같음).
3. analysis-service 가 **그 지점의 규칙들**로 사진을 판독해 규칙마다 등급을 매긴다. ← 새로
4. 등급이 경고 · 비상이면 **경고**를 만든다. ← 새로
5. 대시보드에 등급 색으로 뜨고, 누르면 근거 사진이 보인다.
6. 사람이 확인하거나, 다음 점검에서 정상으로 돌아오면 경고가 풀린다. ← 새로

### 두 로봇: 터틀봇과 젯봇

소방 관제는 두 로봇 모두 한다. 웹은 로봇 종류를 가리지 않고 **같은 미션 경로**로 보낸다 — 지금도 점검 계획마다 로봇을 고르므로, 젯봇이 같은 토픽 계약을 지키면 웹 코드는 바뀌지 않는다.

| | 터틀봇 | 젯봇 |
| --- | --- | --- |
| 지점까지 이동 | `/inspection/goal` → Nav2 (`nav2_goal_bridge.py`, 있음) | **같은 계약 `/inspection/goal` → 젯봇 자체 주행**(위치 추정 4.1 + 경유점 따라가기 4.3). 결과도 같은 `/inspection/goal_status` 와 사유 코드로 낸다 |
| 촬영 · 사진 전송 | 있음 | 같은 경로(스테레오 중 한쪽 카메라 사진) |
| 판독 | analysis-service | 같음. 점검 사진은 서버에서 판독한다(젯봇 안에서 도는 것은 순찰 중 실시간 `THERMAL` 뿐) |
| 도착 정확도 | 위치 0.12m · 방향 0.15rad | 실측 전. 터틀봇보다 나쁠 것으로 보고 설계한다(아래) |
| 시작 조건 | 바로 가능 | 젯봇 기반 작업(4.0)과 위치 추정(4.1)이 끝난 뒤 |

**젯봇의 도착 오차를 감당하는 방법** — 규칙의 "영역"을 로봇이 정확히 같은 자리에 선다는 전제로만 쓰면 젯봇에서 틀린다.

- 판독기가 먼저 **대상을 사진에서 찾고**(소화기 사각형, 계기판 원, 표시등), 그 다음 판정한다. 영역은 "이 근처에 있어야 한다"는 넓은 범위로만 쓴다.
- 규칙의 영역 · 기준 사진은 **로봇 종류별로** 둔다(카메라 높이와 화각이 달라 같은 지점이라도 사진이 다르다).
- 젯봇 위치는 작업 중 오차가 쌓인다(대기 구역 마커로 작업 전후에만 정렬, 4.1). 뒤쪽 지점일수록 여유를 크게 본다.
- 젯봇의 도착 허용 오차는 실측해서 정한다. 넘으면 지금의 "확인 불가" 경로(`NAV_FAILED` 등)로 보고한다.

**순서:** 터틀봇으로 전체 경로(규칙 → 판독 → 등급 → 경고)를 먼저 완성하고, 젯봇은 준비되는 대로 같은 경로에 붙인다.

### 등급

| 등급 | 뜻 | 대시보드 |
| --- | --- | --- |
| `NORMAL` 정상 | 규칙에 맞다 | 초록, 경고 없음 |
| `WARNING` 경고 | 벗어났지만 급하지 않다 | 주황, 경고 목록 |
| `EMERGENCY` 비상 | 바로 조치해야 한다 | 빨강, 목록 맨 위 · 머리줄 상태 |
| `UNKNOWN` 판독 불가 | 사진이 나쁘거나 대상을 못 찾음 | 회색, "확인 필요" (지금의 재촬영 후보와 같은 취급) |

지점의 등급은 그 지점 규칙들 가운데 **가장 나쁜 등급**이다. 사람 판정(정상 · 이상)은 지금처럼 AI 등급과 따로 쌓고, 사람 판정이 있으면 그것이 우선한다.

### 핵심 설계: 규칙 = 판독기 종류 + 설정 + 등급 기준

규칙을 코드에 박지 않고 지점마다 설정으로 둔다. 판독기 종류만 코드이고, "어느 지점에서 무엇을 어떤 기준으로"는 전부 설정이다.

| 판독기 종류 | 보는 것 | 설정 | 등급 기준 예 |
| --- | --- | --- | --- |
| `OBJECT` 물체 유무 · 위치 | 소화기가 제자리에 있는가, 통로에 적치물이 없는가 | 물체 이름, 있어야/없어야, 기대 영역 | 제자리 = 정상 · 영역 밖 = 경고 · 없음 = 비상 |
| `GAUGE` 계기판 바늘 | 압력계 · 온도계 값 | 눈금 영역, 최소 · 최대 각도와 값, 구간 | 정상 구간 / 경고 구간 / 비상 구간 |
| `LAMP` 표시등 색 | 경보등 · 상태등 | 등 영역, 색별 등급 | 초록 = 정상 · 노랑 = 경고 · 빨강 = 비상 |
| `THERMAL` 열화상 | 열원의 크기 · 세기 | 색상표, 기준 비율 | 열원 없음 = 정상 · 작음 = 경고 · 큼 = 비상 (4.2 와 같은 코드) |

- 한 지점에 규칙을 여러 개 둘 수 있다(예: P1 에 소화기 `OBJECT` + 압력계 `GAUGE`).
- 영역은 기준 사진 위에서 지정하고 도착 오차만큼 여유를 둔다(터틀봇: 위치 0.12m · 방향 0.15rad. 젯봇은 위 "두 로봇" 참고).
- 판독기 종류를 더할 때는 analysis-service 에 함수 하나(`check(사진, 설정) → 등급 · 근거`)를 등록한다. 그 밖의 경로(큐 · 저장 · 경고 · 화면)는 바뀌지 않는다.

### 서비스별 변경

| 서비스 | 변경 |
| --- | --- |
| inspection-service | `inspection_rule` 표(지점 · 판독기 종류 · 설정 JSON(로봇 종류별 영역 포함) · 등급 기준 · 사용 여부 · 대상의 지도 좌표 · 위치 기준으로 사용 여부(4.1)), `rule_result` 표(관측 · 규칙 · 등급 · 근거 JSON · 모델 버전) 추가(Flyway). 결과가 오면 경고를 만들거나 푼다(3.1) |
| analysis-service | 품질 검사 뒤에 그 지점의 규칙을 받아 판독기 실행. 품질이 `RETAKE` 면 전부 `UNKNOWN` |
| 화면(관리자) | 지점 편집에 규칙 목록, 기준 사진 위에서 영역 · 눈금 지정, 등급 기준 입력 |
| 화면(사용자) | 관측 상세에 규칙별 등급과 근거(사각형 · 바늘 각도 · 읽은 값) 겹쳐 보기, 확인 · 수정 |
| 대시보드 | 지점 핀 · 지점 현황을 등급 색으로, 경고 종류 `RULE_WARNING` · `RULE_EMERGENCY` 등록 |
| 시뮬레이션 | 대상 상자를 소화기 모델 · 계기판 그림 · 표시등으로 교체(`world_spec.py`). 시연 도구 `target.sh`(치우기 · 옮기기 · 계기판 값 바꾸기) |
| 젯봇(`ros/patrol`) | `/inspection/goal` 계약 구현(4.3), 도착 뒤 촬영 · 사진 전송. 고정 대상을 찾는 가벼운 인식(계기판 · 표시등)을 젯봇 안에서 돌려 위치 보정(4.1) — 판독기 코드의 "대상 찾기" 부분을 같이 쓴다(3.2) |
| 시험 | E2E(전 구간 시험, `scripts/e2e_test.py`)에 규칙 종류마다 정상 · 경고 · 비상 한 번씩. 젯봇은 실기 확인 목록으로 따로 둔다(시뮬레이션에 젯봇이 없다) |

### 단계

1. 경고 저장(3.1)
2. `inspection_rule` · `rule_result` 표, 판독기 틀(3.2), 관리자 화면
3. `LAMP` · `GAUGE` 판독기 — 학습 없이 영상 처리로 되므로 먼저 만들어 전체 경로를 검증한다
4. `OBJECT` 판독기 — 소화기 인식 모델(ROADMAP.md), 시뮬레이션 소화기 모델 교체
5. 대시보드 · 사용자 화면에 등급 표시
6. `THERMAL` 판독기 — 시나리오 1 과 공용
7. 젯봇을 같은 경로에 붙인다(4.0 · 4.1 · 4.3 이 끝난 뒤): 목표 계약, 로봇 종류별 영역, 실기 확인

### 완료 기준

- 소화기를 치우거나 계기판 값을 바꾸고 점검하면, 설정한 기준대로 경고 또는 비상이 대시보드에 뜨고 근거가 보인다.
- 되돌리고 다시 점검하면 스스로 정상으로 돌아온다.
- 이미 있는 판독기 종류의 새 규칙은 코드 변경 없이 관리자 화면에서 더할 수 있다.
- 같은 점검 계획을 로봇만 젯봇으로 바꿔 실행해도 같은 등급이 나온다.

## 3. 공용 바탕

### 3.1 경고 저장

지금 대시보드 경고는 관측 · 작업 표에서 매번 계산한다(`DashboardController.alerts`). 확인 · 해제와 새 출처(젯봇)를 받으려면 표가 필요하다.

- `alert` 표(inspection-service): 종류 · 등급(`WARNING`/`EMERGENCY`) · 상태(`OPEN` → `ACKED` → `RESOLVED`) · 위치(지점 또는 지도 좌표) · 가리키는 대상(관측 · 작업 · 사건) · 근거(JSON) · 시각 · 처리한 사람
- 같은 대상 · 같은 종류의 열린 경고는 하나만 둔다. 등급이 바뀌면 그 줄의 등급을 고친다.
- API: 목록(GET), 확인 · 해제(POST — 사용자 역할만. 대시보드 계정은 조회만이므로 지금 게이트웨이 규칙 그대로 막힌다)
- 대시보드는 계산식 대신 이 표를 읽는다. 화면이 받는 모양(`type · severity · ref`)은 그대로라 패널은 바뀌지 않는다.

### 3.2 판독기

- 위치: `web/python/analysis-service/src/checkers/` 에 종류마다 파일 하나. 입력은 사진과 설정, 출력은 등급과 근거다.
- **같은 코드를 두 곳에서 쓴다**: analysis-service(점검 사진 판독)와 젯봇. 젯봇에는 `THERMAL` 판독(순찰 중 실시간)과 `GAUGE` · `LAMP` 의 "대상 찾기" 부분(위치 보정용, 4.1)을 올린다. 그래서 판독기는 "대상 찾기"와 "판정"을 나눠 만든다.
- 학습 모델이 필요한 것은 `OBJECT` 뿐이다. `GAUGE` · `LAMP` · `THERMAL` 은 색 · 도형 처리로 시작하고, 오판이 많으면 모델로 바꾼다(출력 모양이 같으므로 다른 곳은 그대로다).

### 3.4 ROS 2 배포판: Jazzy (Humble 에서 옮김)

젯봇 · 터틀봇 · 브리지 노드는 **같은 배포판**을 쓴다. 실제 터틀봇(라즈베리파이)이 Jazzy 라 시뮬레이션도 Jazzy 로 옮겼다(브랜치 `feat/jazzy`).
노드 · 토픽 구성은 그대로이고, **서비스(Spring · Python · 화면 · DB)에는 변경이 없다** — 서비스는 rosbridge 의 토픽 계약만 본다.

**지킬 것**

- 우리 노드(`nav2_goal_bridge.py`, `cmd_vel_watchdog.py`, 새로 쓸 `launcher_bridge.py` · `ros/patrol`)는 rclpy 와 표준 메시지만 쓴다. 배포판마다 다른 API 는 피한다.
- 배포판 이름을 파일에 직접 적지 않는다. 도커 이미지는 빌드 인자 `ROS_DISTRO`(`compose.yaml` 한 곳, 기본 `jazzy`)로 받고, 스크립트는 `/opt/ros/$ROS_DISTRO/setup.bash` 를 쓴다.
- 바퀴 명령 `/cmd_vel` 은 Jazzy 에서 `geometry_msgs/TwistStamped` 다. 우리 노드는 환경 변수 `CMD_VEL_STAMPED`(기본 1, 0 이면 `Twist`)로 고른다. 서버와의 약속 `/cmd_vel_teleop` 은 그대로 `Twist` 이고 워치독이 감싼다.
- 웹 쪽(robot-service)은 rosbridge 의 토픽 계약만 보므로 배포판과 무관하다.

**Humble → Jazzy 에서 바꾼 것**

| 대상 | Humble 때 | Jazzy 로 바꾼 것 |
| --- | --- | --- |
| 시뮬레이션 이미지 `ros/sim/Dockerfile` | `ros:humble-ros-base` + `ros-humble-*` | `ros:${ROS_DISTRO}-ros-base` + `ros-${ROS_DISTRO}-*`, `ros-gz` |
| 시뮬레이터 | Gazebo Classic 11 (`gazebo_ros`) | Gazebo Harmonic(`gz sim`). 로봇 생성 `ros_gz_sim create`, 토픽은 `ros_gz_bridge`(TurtleBot3 Jazzy 설정), 카메라는 `ros_gz_image` |
| 월드 `world_spec.py` | 플러그인 `gazebo_ros_state`, `model://ground_plane · sun`, 사진 판 `.material` 스크립트 | Harmonic 시스템 플러그인(Physics · UserCommands · SceneBroadcaster · Sensors · Imu), 땅 · 해 직접 정의, 사진 판 PBR 텍스처 |
| 시뮬레이션 도구(`gz.py` · `obstacle.py` · `nav_soak.py`) | `/spawn_entity` · `/delete_entity` · `/gazebo/set_entity_state` | `/world/factory/create` · `remove` · `set_pose`(`ros_gz_interfaces`), 모델 목록은 `gz model --list` |
| Nav2 설정 `nav2_params.yaml` | Humble 기준 | 플러그인 이름 `::`, `recoveries_server` → `behavior_server`, `plugin_lib_names` 삭제 · `navigators` 명시, `enable_stamped_cmd_vel`, 새 서버(`velocity_smoother` · `collision_monitor` · `docking_server` · `route_server`) 설정, 행동 트리 `BTCPP_format="4"`. 튜닝값(Theta* · MPPI · 팽창 · AMCL)은 그대로 |
| 실행 스크립트 | `source /opt/ros/humble/setup.bash` | `source /opt/ros/$ROS_DISTRO/setup.bash` |
| 시뮬레이션 오도메트리 | Classic 바퀴 계산(정확) | Harmonic 바퀴 계산(DiffDrive)은 회전 · 빠져나오기 때 바퀴가 헛돌아 방향이 크게 틀어졌다(e2e 한 번에 67°). AMCL 오차 계수 0.05(시뮬레이션 odom 이 정확하다는 전제)로는 따라잡지 못해 위치가 1m 넘게 밀렸다 → 바퀴 구동은 DiffDrive 그대로, odom 은 Gazebo OdometryPublisher(로봇의 실제 움직임)로 낸다(`SIM_TRUE_ODOM`). 위치 추정 오차 4~6cm |
| 시뮬레이션 저장 지도 | `site`(Classic 에서 SLAM) | 기본을 설계도 지도 `reference`(`world_spec.py`, 월드와 같은 정의)로(`SIM_MAP`). `site` 는 Harmonic 월드와 어긋나(C2 동쪽 벽 윗부분 · 선반 몸통 없음) 벽이 새 장애물로 잡히고 위치 추정이 0.6~1.2m 밀렸다. `site` 는 남겨 둔다 |
| 시뮬레이션 부담(GPU 없이 CPU 로 그림) | 시계 `/clock` 10Hz, 라이다는 CPU 광선(`ray`) | Harmonic 은 라이다(`gpu_lidar`) · 카메라를 그려서 만든다. 시계 · 바퀴 관절 상태가 물리 한 걸음(4ms)마다 나와 모든 노드가 초당 160번 넘게 깨어났다 → 시계는 `clock_relay.py` 가 50Hz 로, 관절 상태는 30Hz 로 줄이고, 카메라는 누가 영상을 받을 때만 5Hz(아니면 0.5Hz)로 그린다(`camera_gate.py`, 신호를 받을 때만 그리는 카메라). Nav2 서버 열네 개를 한 프로세스로 합치고(`use_composition`, 따로 돌 때 가만히 있어도 합쳐 2코어 남짓), 물리 한 걸음을 8ms 로 늘렸다. 시뮬레이션 속도(실제 시간 대비) 0.65 → 0.95(주행 중 0.94, 관제 카메라를 볼 때 0.8 안팎). 실제 로봇과는 관계없다 |
| 터틀봇 실기 | — | 라즈베리파이 Ubuntu 24.04 + Jazzy 로 이미 세팅(카메라 `camera_ros`) |
| 젯봇 | 기반 작업의 결과물(4.0) | Jetson Nano 는 기본 OS 가 오래되어 도커로 같은 판을 올린다. 기반 작업 쪽에서 확인 |

시뮬레이션은 GPU 없이 소프트웨어로 그려 Classic 보다 느리다(실제 시간보다 느리게 흐른다. 시뮬레이션 시간 기준 로봇 속도는 같고, 실제 로봇과는 무관). 주행 품질 수치(`drive_probe.py` · `nav_soak.py`)는 Jazzy 에서 다시 재야 한다.

**기반 작업을 기다리지 않고 할 수 있는 것:** 4장의 단계 1~3(사건 흐름 · 투척 모드 · 대시보드)은 `fire.sh` 로 젯봇 보고를 흉내 내므로 젯봇 없이 끝까지 만들고 시험할 수 있다. 젯봇이 필요한 것은 단계 4~5 뿐이다.

### 4.1 젯봇 위치 추정 — 대기 구역 마커 하나로 정렬

**조건**

- 젯봇에는 엔코더 · 라이다가 없다(README 제원). 터틀봇처럼 라이다 + AMCL 을 쓸 수 없다. 쓸 수 있는 것은 같은 방향을 보는 스테레오 카메라뿐이다. 연산은 Jetson Nano 4GB.
- 두 로봇이 **같은 지도, 같은 좌표계**를 써야 한다. 젯봇이 본 화재 위치로 터틀봇이 가야 하기 때문이다.
- 실제 공간 곳곳에 마커를 붙이는 것은 부자연스럽다. **정렬 기준은 가능한 한 ArUco 마커 1개**로 한다.

**정해진 방식**

1. **대기 구역 1곳**(시작점 · 충전 자리)을 두고 그곳에 ArUco 마커를 하나 둔다.
2. **작업 단위 = 작업(순찰) 계획 1개.** 작업의 시작과 끝이 모두 이 마커다.
   - **시작 전 정렬:** 마커를 보고 젯봇의 지도 위 위치 · 방향을 맞춘 뒤 출발한다.
   - **작업 중:** 마커 없이 스테레오 비주얼 오도메트리로만 위치를 잇는다. 이 동안 오차가 쌓인다.
   - **종료 후 정렬:** 대기 구역으로 돌아와 마커로 다시 정렬하고 끝낸다. 쌓인 오차는 여기서 0 으로 돌아간다.
3. 오차는 작업 하나 안에서만 쌓이고 다음 작업으로 넘어가지 않는다. 카메라만 쓰는 구조에서는 이것이 기본 방식이다.
4. **작업 중 보정:** 고정된 점검 대상(계기판 · 표시등)을 봤을 때 그 대상의 지도 좌표로 위치를 바로잡는다(아래 "점검 대상 기준 위치 보정"). 마커를 더 붙이지 않는다.
5. **그래도 실측에서 오차가 크면** 대기 구역 외에 정렬 구역 1~2곳을 더해 작업 중간에 정렬한다. 마커는 그만큼만 늘린다.

**같은 지도가 되는 이유**

- 지도는 터틀봇이 만든 `ros/maps/site.*` 하나다. 젯봇은 지도를 만들지 않는다.
- 대기 구역 마커의 지도 좌표를 `ros/maps/markers.yaml` 에 적는다(지금은 한 줄. 정렬 구역을 더하면 줄이 는다).
- 좌표는 **터틀봇으로 등록한다**: AMCL 로 자기 위치를 아는 터틀봇이 카메라로 마커를 보면 "터틀봇 위치 + 마커까지의 상대 위치 = 마커의 지도 좌표"가 나온다. 여러 번 본 값을 평균한다. 지도를 다시 만들면 다시 등록한다.
- 젯봇은 정렬할 때 마커의 네 모서리로 자기 자세를 구하고(PnP, 스테레오로 거리 보강) 마커 좌표를 거꾸로 적용한다. 그래서 정렬 직후의 젯봇 좌표는 터틀봇 지도 좌표와 같다.
- 결과는 터틀봇과 같은 토픽 계약(`/inspection/map_pose`)으로 낸다. robot-service · 대시보드 지도는 젯봇을 터틀봇과 똑같이 그린다.

**작업 한 번의 순서 (젯봇 안)**

| 순서 | 하는 일 | 실패하면 |
| --- | --- | --- |
| 1 | 대기 구역에서 마커 확인 → 위치 맞춤 | 마커가 안 보이면 출발하지 않고 보고(`NAV_UNAVAILABLE`) |
| 2 | 계획의 지점을 차례로 방문(오도메트리로 위치 추정). 고정 대상을 본 지점에서는 대상 기준으로 위치 보정 | 추적을 잃으면 멈추고 "위치 불확실" 보고 |
| 3 | 대기 구역으로 복귀: 추정 위치 근처까지 온 뒤 제자리에서 돌며 마커를 찾는다 | 못 찾으면 멈추고 보고 → 사람이 옮긴다 |
| 4 | 마커를 보면서 정해진 자리 · 방향으로 접근해 멈춘다(충전 자리) | — |
| 5 | **복귀 오차 기록:** 마커로 구한 실제 위치와 그 직전 추정 위치의 차이 | — |

**복귀 오차를 지표로 쓴다**

- 5번 값은 "이번 작업에서 쌓인 오차"다. 작업마다 저장하고 대시보드 로봇 상세에 보여 준다.
- 이 값으로 정한다: 작업 하나의 적정 길이, 정렬 구역을 더할지(5번), 스테레오 보정을 다시 할지.

**오차가 다른 기능에 미치는 영향과 대비** — 마커를 늘리지 않고 감당하는 방법이다.

| 영향 | 대비 |
| --- | --- |
| 화재 좌표가 틀어진다(작업 뒤쪽일수록) | 터틀봇이 도착한 뒤 자기 카메라로 다시 찾는다(흐름 7단계). 안 보이면 제자리에서 돌며 찾고, 찾은 방향으로 조준한다. 터틀봇 위치는 라이다로 정확하므로 젯봇 좌표는 "근처"만 맞으면 된다 |
| 점검 지점에 어긋나게 선다(시나리오 2) | 판독기가 대상을 사진에서 먼저 찾고 판정한다(2절 "두 로봇"). 대상이 화면에 없으면 "확인 불가"로 보고 |
| 작업이 길수록 나빠진다 | 계획 하나의 길이를 복귀 오차 실측으로 제한한다. 넓은 구역은 계획을 나눈다(계획 사이에 대기 구역에서 정렬) |

**점검 대상 기준 위치 보정 (계획에 포함)**

마커를 늘리지 않고 작업 중 오차를 줄이는 방법이다. 점검 대상은 이미 그 자리에 있고 지도 좌표를 알 수 있으므로, 대상을 봤을 때 젯봇 위치를 바로잡는다. 공간에 아무것도 더 붙이지 않는다.

- **원리:** 판독기가 사진에서 대상을 찾으면 스테레오로 대상까지의 방향 · 거리를 잰다. "대상의 지도 좌표 − 대상까지의 상대 위치 = 젯봇의 지도 위치"다. 마커 정렬과 같은 계산이고, 기준만 마커 대신 대상이다.
- **대상 좌표 등록:** 규칙에 대상의 지도 좌표(`target_x` · `target_y`, 벽에 붙은 것은 바라보는 방향도)를 둔다. 마커와 같은 방법으로 **터틀봇이 등록한다**(자기 위치 + 대상까지의 상대 위치, 여러 번 평균). 지도를 다시 만들면 다시 등록한다.
- **기준으로 쓸 수 있는 대상:**

| 대상 | 기준으로 쓰나 | 이유 |
| --- | --- | --- |
| 계기판 · 표시등(벽에 고정) | 쓴다 | 움직이지 않는다. 모양(원 · 사각형)에서 방향까지 구할 수 있다 |
| 소화기(옮겨질 수 있음) | 쓰지 않는다 | "제자리에 있는가"가 바로 점검 내용이다. 이것으로 위치를 맞추면 옮겨진 소화기를 정상으로 보게 된다 |
| 열화상 인쇄물 | 쓰지 않는다 | 화재 위치는 미리 알 수 없는 값이다 |

  규칙마다 "위치 기준으로 사용" 여부를 설정으로 둔다(기본값: 고정 대상만 켬).
- **적용 조건(잘못된 보정을 막는다):** 인식 확신도가 기준 이상이고, 대상까지 거리가 스테레오가 믿을 만한 범위 안이며, 보정량이 한도(예: 0.5m) 이하일 때만 적용한다. 한도를 넘으면 적용하지 않고 "위치 불확실"로 기록한다 — 대상이 바뀌었거나 다른 물체를 본 것일 수 있다.
- **보정 범위:** 대상 하나로는 거리 방향 오차가 주로 잡힌다. 방향(각도)까지 잡으려면 대상의 모양에서 자세를 구할 수 있어야 한다(계기판 원의 찌그러짐 등). 처음에는 위치만 보정하고 각도는 실측을 보고 더한다.
- **기록:** 보정할 때마다 지점 · 보정량을 작업 기록에 남긴다. 복귀 오차와 함께 보면 어느 구간에서 오차가 쌓이는지 알 수 있다.
- **정렬 구역과의 관계:** 이 보정으로 복귀 오차가 목표 안에 들어오면 정렬 구역(마커 추가)은 필요 없다. 순서는 ① 마커 하나만 → ② 대상 기준 보정 → ③ 그래도 크면 정렬 구역 추가.

**먼저 확인할 것**

| 확인 | 기준(목표값, 실측으로 확정) | 못 미치면 |
| --- | --- | --- |
| 두 카메라의 간격 · 고정 | 간격 6cm 이상, 주행 중에도 서로 움직이지 않게 고정 | 간격을 넓히고 고정대를 보강한다 |
| 두 카메라 보정(내부 · 스테레오) | 보정 뒤 1m 거리 오차 3cm 이내 | 보정판 · 해상도 조정 |
| 정렬 정확도 | 정렬 직후 두 로봇 좌표 차이 0.1m 이내 | 마커를 키우거나 정렬 거리를 줄인다 |
| 마커가 보이는 거리 | 복귀 오차를 감안해 2~3m 밖에서도 인식 | 마커를 키운다(한 변 15~20cm) |
| 복귀 오차 | 시연 경로 한 바퀴 뒤 0.3m 이내 | 대상 기준 보정을 켠다 → 그래도 넘으면 계획을 나누거나 정렬 구역 추가(5번) |
| 대상 기준 보정의 효과 | 켰을 때 복귀 오차가 껐을 때보다 뚜렷이 준다(같은 경로 5회 비교) | 기준으로 쓰는 대상을 줄이거나 적용 조건을 조인다. 효과가 없으면 끈다 |
| Nano 처리 속도 | 오도메트리 + 열화상 판독을 합쳐 5Hz 이상 | 해상도를 낮추거나 판독을 2~3 프레임마다 |

### 4.2 화재 판독 — 열화상 이미지

시연에서는 열화상 카메라 출력 이미지를 인쇄해 시연 공간에 두고, 일반 카메라로 그 인쇄물을 본다. 현업에서는 열화상 카메라 영상이 직접 들어온다. **두 경우가 판독 코드를 같이 쓰도록** 단계를 나눈다.

| 단계 | 시연 | 현업 |
| --- | --- | --- |
| ① 열화상 프레임 얻기 | 카메라 영상에서 인쇄물을 찾아(테두리 사각형) 정면으로 편다 | 열화상 카메라 프레임 그대로 |
| ② 판독(`THERMAL` 판독기) | 색상표로 색 → 상대 온도, 뜨거운 영역의 크기 · 세기 계산 → 등급 | 같음(색 대신 온도 값을 바로 쓴다) |

- 등급: 열원 없음 = 정상, 기준 이하 = 경고, 기준 이상 = 비상. **비상일 때만 터틀봇을 부른다.** 경고는 관제 알림만 한다.
- 인쇄물은 같은 색상표(예: iron)로 통일하고, 테두리를 둘러 찾기 쉽게 한다. 정상 · 경고 · 비상 세 종류를 준비해 바꿔 끼우며 시연한다.
- 오탐 방지: 연속 N 프레임에서 같은 등급일 때만 보고한다.
- **화재의 지도 좌표** = 젯봇 위치(4.1) + 인쇄물까지의 방향 · 거리(스테레오). 이 좌표가 터틀봇의 목적지 계산에 쓰인다.

### 4.3 젯봇 연결 (robot-service)

위치를 터틀봇과 같은 계약으로 내므로 어댑터를 새로 만들지 않고 `RosbridgeRobotAdapter` 를 그대로 쓴다. 젯봇이 내지 않는 것(라이다 · Nav2 경로)은 제공 기능에 "미지원"으로 나온다.

- **쓰는 계약:** `/inspection/map_pose`, `bridge_status`, 영상(web_video_server), 조종(`cmd_vel` + 워치독 — 터틀봇과 같은 코드)
- **이동은 터틀봇과 같은 목표 계약으로 받는다:** `/inspection/goal` → `/inspection/goal_status`(사유 코드도 같음). 터틀봇은 이 계약을 Nav2 로 옮기고(`nav2_goal_bridge.py`), 젯봇은 자체 주행으로 옮긴다(`ros/patrol` 의 브리지). 그래서 점검 미션(시나리오 2)과 순찰(시나리오 1)이 웹에서는 같은 것이다 — **순찰 = 젯봇에게 준 점검 계획**이고, 지금의 예약 · 대기열 · 진행 기록을 그대로 쓴다.
- **자체 주행:** 지도(`site.*`)에서 경로를 구해 경유점을 순서대로 따라간다(위치 → 다음 경유점 방향으로 조향). Nav2 는 쓰지 않는다. 앞이 막히면(스테레오 깊이) 멈추고 `NO_PROGRESS` 로 보고한다.
- **추가 계약(시나리오 1 전용):** `/patrol/detection`(등급 · 화재 지도 좌표 · 확신도 · 사진) — 이동 중에도 실시간으로 본 것을 알린다.
- **화면:** 로봇에 종류(터틀봇 / 젯봇)를 두고 지도 위 모양 · 규칙 영역을 종류별로 쓴다.
- 젯봇 쪽 코드는 `ros/patrol/src/` 에 둔다(위치 추정 · 순찰 · 판독 · 브리지).

### 4.4 사건 처리 (inspection-service)

- `incident` 표: 종류(`FIRE`) · 지도 좌표 · 등급 · 감지한 로봇 · 근거 사진 · 상태 · 대응 로봇 · 투척 모드(생성 시점 값).
- 상태: `DETECTED` → `DISPATCHED` → `ARRIVED` → (`AWAITING_APPROVAL`) → `LAUNCHED` → `RESOLVED` / `FAILED` / `DISMISSED`(오탐으로 닫음). `task_event` 처럼 추가만 하는 기록으로 남긴다.
- **투척 위치:** 화재 좌표에서 사거리만큼 떨어지고 화재를 바라보는 자세들 가운데, 지도에서 비어 있고 사이에 벽이 없으며 가장 가까운 것을 고른다. 갈 수 없으면(`BLOCKED_NO_PATH`) 다음 후보로 넘어간다.
- **가로채기:** 대응 로봇이 점검 중이면 그 작업을 취소 요청하고(`CANCEL_REQUESTED` 경로 재사용), 끝나는 즉시 출동 임무를 보낸다. 예약 실행 버퍼(`ScheduleService`)는 사건이 닫힐 때까지 그 로봇의 회차를 붙잡아 둔다.
- 출동 임무는 지금의 미션과 같은 경로(멱등 · outbox)를 쓰되 종류가 `RESPONSE` 다.

### 4.5 투척 — 두 모드와 명령 계약

투척 기구(아두이노 + SG90 로 쇠구슬 발사)는 터틀봇에 달리는 실물 디바이스다. 쏠지 말지는 서버가 판단하고, 기구는 명령을 실행한다. 명령의 정확한 모양은 [INTERFACES.md](INTERFACES.md) 2.2 · 7장(F1)에 있다.

| | 사람 승인 모드 `APPROVAL` | 자동 투척 모드 `AUTO` |
| --- | --- | --- |
| 출동 | 자동 | 자동 |
| 도착 뒤 | `AWAITING_APPROVAL` 에서 멈추고 관제에 승인 요청. 터틀봇 영상과 재판독 결과를 보여 준다 | 터틀봇 카메라로 재판독해 **비상이 다시 확인되면** 바로 투척 |
| 투척 조건 | 사용자 역할이 승인 단추를 누름 | 재판독 = 비상 + 화재가 사거리 · 조준 범위 안 |
| 조건을 못 채우면 | 정한 시간 안에 승인이 없으면 대기 유지 + 재알림 | 투척하지 않고 승인 모드로 넘긴다 |

- **모드 설정:** 현장 설정 하나(`launch_mode`). 1 관리자 이상만 바꾸고 감사 로그에 남는다. 대시보드 머리줄에 지금 모드를 늘 표시한다. 사건은 만들어질 때의 모드를 갖고 간다(도중에 설정을 바꿔도 진행 중인 사건은 그대로).
- **명령 토픽:** `/inspection/actuator`(명령 ID · 종류 `LAUNCH` · 횟수) → `/inspection/actuator_status`(명령 ID · `DONE`/`FAILED` · 사유). 이동 계약과 같은 모양이다.
- **로봇 쪽:** `ros/robot/src/launcher_bridge.py` 가 토픽을 받아 아두이노에 시리얼로 전달한다(실로봇 전용). 시뮬레이션에는 답만 하는 모의 노드를 둔다.
- **`RobotAdapter`:** `actuate(commandId, kind)` 와 제공 기능 `launcher` 추가.
- **안전(두 모드 공통):** 도착 확인 뒤에만, 명령 ID 로 한 번만 실행한다. 비상 정지는 투척도 막는다. 투척 뒤 재판독해 결과(여전히 비상인지)를 사건에 남긴다.

### 4.7 시뮬레이션 · 시험

- 젯봇은 Gazebo 에 넣지 않는다. 대신 터틀봇이 점검(순찰)하는 동안 서버가 1.5초마다 카메라 사진을 열화상 판독한다(**순찰 감시**, inspection-service `PatrolWatchService`). 판이 충분히 크게 보이고 같은 등급이 연속 2번 나오면, 판의 방향 · 로봇 위치로 지도에서 그 방향의 벽을 찾아(robot-service `raycast`) 감지 보고와 같은 길(`IncidentService.detect`)로 넣는다.
- 월드에는 열화상 사진 판(시연 사진: 무지개 색표, 15~300°C)을 순찰 경로에서 보이는 고정 자리 두 곳에 늘 걸어 둔다(`world_spec.THERMAL_SPOTS`: C2 복도 동쪽 벽(문 맞은편) `c2_east` · 전기실 문 옆 벽 `elec_door`). 점검 지점 정지 사진에는 찍히지 않는 자리다. `fire.sh set <자리> normal|warning|emergency` 는 사진만 바꾸고, `fire.sh detect` 는 오탐 시험용 가짜 보고만 보낸다. 투척을 마치면 sim 의 `sim_control.py` 가 몇 초 뒤 화재 사진을 꺼짐으로 바꾼다(불이 꺼진 것처럼).
- 비상(화재)은 하던 점검을 멈추고 출동 · 투척, 경고(과열)는 하던 점검을 멈추고 그 앞 1m 에서 몇 번 찍어 확인한다(사건 종류 `HEAT`, 투척 없음): 과열이면 사진과 함께 열원 경고, 정상이면 기록만, 화재로 커졌으면 화재 사건으로 바꿔 이어 간다. 사건이 끝나면 멈춘 점검을 남은 지점부터 이어 간다. 그 자리에 열린 열원 경고가 있으면 다시 들르지 않고, 다음 순찰에서 정상으로 보이면 경고를 푼다.
- E2E(`scripts/e2e_scenarios.py --only fire`): 순찰 중 화재 발견(승인 모드 · 자동 모드) → 점검 멈춤 → 도착 → 재판독 → 투척 → 불이 꺼져 해결 → 순찰 이어 가기 / 순찰 중 과열 발견 → 확인 → 경고 → 순찰 이어 가기 → 열린 경고가 있으면 들르지 않음 → 정상이면 경고 해제 / 오탐(사진은 정상인데 보고만 옴) / 닫은 뒤 다시 열기.

### 단계

1. 경고 저장(3.1), `THERMAL` 판독기(3.2), 투척 명령 계약과 모의 노드 — 하드웨어 없이 흐름 전체를 먼저 돌린다
2. `incident` 표와 상태 흐름, 투척 위치 계산, 출동 임무, 가로채기, 두 모드
3. `fire.sh` 와 E2E, 대시보드 사건 패널 · 상세, 사용자 승인 화면
4. **(젯봇 기반 작업이 끝난 뒤)** 젯봇 위치 추정: 카메라 보정 → 대기 구역 마커 등록(터틀봇) → 시작 정렬 · 오도메트리 · 복귀 정렬 → 복귀 오차 측정 → 대상 좌표 등록(터틀봇) · 대상 기준 보정 → 켰을 때와 껐을 때 비교(4.1 의 확인 표)
5. 젯봇 순찰 · 판독 · 보고, robot-service 연결, 대시보드 지도에 젯봇
6. 실로봇: `launcher_bridge.py` ↔ 아두이노, 사거리 · 조준 보정
7. 통합 시연

### 완료 기준

- 젯봇이 비상 등급 열화상 이미지를 보면 대시보드에 비상 경고가 뜨고, 지도에 화재 위치가 찍힌다.
- 터틀봇이 그 좌표의 투척 위치에 도착하고, 승인 모드에서는 승인 뒤에, 자동 모드에서는 재판독 확인 뒤에 투척 명령을 한 번 실행한다.
- 대기 구역에서 정렬한 직후 두 로봇의 지도 좌표가 0.1m 이내로 일치하고, 작업마다 복귀 오차가 기록된다.
- 점검 중이던 터틀봇도 출동하고, 사건이 끝나면 밀린 예약 점검이 이어진다.

## 5. 미정 항목과 구현 후 작업

**미정 항목은 계획을 막지 않는다.** 값 · 대상 · 규격이 정해지지 않은 것은 모두 설정 자리를 만들어 두고, 정해지는 대로 값만 넣는다. 목록과 받는 자리는 [INTERFACES.md](INTERFACES.md) 8장에 있다.

| 미정 항목 | 받는 자리 |
| --- | --- |
| 계기판 · 표시등의 실제 대상, 등급 기준 값 | 규칙의 설정 · 등급 기준(화면에서 입력). 새 종류는 판독기 파일 추가 |
| 열화상 인쇄물의 규격 · 색상표, 열원 기준 | `THERMAL` 판독 설정 |
| 투척 사거리 · 조준 범위 · 기구 추가 값 | 설정 `launch.*` |
| 투척 기구의 시리얼 형식 | `launcher_bridge.py` 파라미터(토픽 계약과 서버는 그대로) |
| 대기 구역 위치, 마커 크기 · 높이, 정렬 구역 추가 | 마커 표 |
| 위치 기준으로 쓸 고정 대상 | 규칙의 대상 좌표 · 사용 여부 |
| 젯봇 쪽 토픽 이름, 허용 오차, 카메라 제원 | 로봇 설정 |
| ROS 2 배포판 | Jazzy 로 옮김. 서비스에는 변경이 없다(3.4) |

**실측은 구현 후 작업이다.** 장비와 구현이 있어야 잴 수 있으므로 계획 단계에 넣지 않는다. 이 문서에 적힌 정확도 · 속도 수치는 모두 목표값이고, 실측 결과는 위 설정값으로 들어간다. 목록은 [INTERFACES.md](INTERFACES.md) 11장에 있다(젯봇 정렬 · 복귀 오차 · 도착 정확도 · 처리 속도, 스테레오 거리 오차, 투척 사거리 · 편차, 판독기별 오판 비율).
