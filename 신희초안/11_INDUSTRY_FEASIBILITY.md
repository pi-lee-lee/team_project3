## 구현 가능성을 판단하는 기준

현재 사용자 조건은 TurtleBot3·로봇 카메라·LiDAR·별도 PC다. JetBot MINI는 활용하는 방향을 기본 전제로 기획하고 실제 참여 범위는 세팅·연동 결과로 구체화한다. 열화상·가스·실제 설비 통신·투척 장치는 확보·연동을 확인하지 않았다. 현재 환경에서 정상 주행·촬영·전송을 시험한 결과도 이번 조사에 포함하지 않는다.

| 구분 | 이 문서의 의미 |
| --- | --- |
| 현재 장비로 설계 가능한 범위 | 알려진 장비 종류로 시험을 시작할 수 있는 기능. 구현 완료·성공 보증과 구별 |
| 추가 장비·접근 권한이 필요한 범위 | 열화상·가스·설비 데이터처럼 관측 수단을 더 확보해야 하는 기능 |
| 실제 검증이 필요한 범위 | 장비 모델·설치·통로·촬영·API·데이터를 확인해야 판단 가능한 기능 |

TurtleBot3 공식 사양은 모델별 카메라·센서 구성이 다름을 보여 준다. 실제 모델과 설치 버전에서 영상 해상도·시야·노출, LiDAR 스캔 높이, 상태 메시지와 단위를 확인한다. 배터리·센서·구동 상태 조회 가능 범위를 로봇마다 따로 적는다. JetBot MINI라는 이름만으로 LiDAR·엔코더·Odometry·ROS2 지원을 가정하지 않는다. [ROBOTIS 사양](https://emanual.robotis.com/docs/en/platform/turtlebot3/features/)

## 감지 대상과 교육용 표현

| 대상 | 교육용 시험에서 확보할 수 있는 것 | 실제 현장 감지를 판단하려면 필요한 것 |
| --- | --- | --- |
| 인쇄·화면의 불 그림 | 표적 위치·종류·촬영 조건별 인식 결과 | 실제 화염 데이터·분광 특성·시야·오탐원에 대한 별도 평가 |
| 표시등·계기 모형 | 현재 표시의 사진과 사람의 판독, 선택적 자동 판독 | 실제 계기 종류·표시 규칙·오류 상태·촬영 조건 |
| 가상 온도·경보 | 주입한 값의 전달·기록·업무 전환 | 실제 센서의 측정 위치·단위·보정·고장 특성 |
| 표면 온도 | 현재 RGB 장비의 직접 측정 범위에 포함되지 않음 | 방사온도 데이터를 제공하는 열화상 또는 적절한 온도 센서 |
| 연기·유해 가스 | 모의 이벤트·기록 파일로 처리 흐름 시험 | 대상 물질·농도·센서 감응·배치·환기·교정·검출 한계 |
| 배터리 내부 고장 | 외관과 가상 BMS 데이터의 연결 시험 | 해당 화학계·팩 설계·BMS·열·가스 데이터와 신뢰할 정답 |
| 통로 상태 | LiDAR 높이에서의 관측, RGB로 보이는 가림·장애물 기록 | 상부·하부·유리·차체·경사 등 미관측 영역의 추가 확인 |
| 모형 대응 | 비위험성 표적과 모형의 도달·실행 기록 | 실제 소화 성능·현장 투입 적합성은 별도 검증 |

RGB 사진의 붉은 영역을 온도 수치로 바꾸거나 색 입힌 모의 열화상을 실측 데이터로 저장하면 해석이 왜곡된다. 열화상 장비를 추가하더라도 측정 대상은 표면이며 거리·방사율(표면의 적외선 방출 특성)·반사 등 조건을 확인해야 한다. 닫힌 패널 내부의 정상 여부를 표면 사진 한 장으로 판정하지 않는다. [FLIR 측정 설명](https://docs.flir.com/T810603/en-US/latest/s07.html)

실제 화염·유해 연기·배터리 가열·열폭주·폭발성 물질 없이 시연한다. 모의 값과 실측 값, 사람이 정한 상태와 모델 출력에 각각 출처를 남긴다. 낮은 카메라에 맞춰 모형을 배치한 결과에는 그 높이와 거리도 적는다.

## 실습실 1개 + 산업 현장 10개의 구현 검토

각 항목의 현장 센서는 필요한 감지 목표를 정할 때 검토할 예다. 분야 전체에 일괄 적용하는 필수 사양으로 확정하지 않는다. 산업 안전 조건과 실제 사례의 근거는 [상세 조사](10_INDUSTRY_FIRE_RESEARCH.md)를 따른다.

<a id="lab"></a>
### 실습실 자체의 운영 문제

아래는 실습실을 실제 사용자 환경으로 택할 때의 추가 검토안이다. 뒤의 산업 10개 후보와 해당 상세 근거는 유지한다. 실습실 안에 산업 모형을 만드는 경우에는 뒤에서 해당 산업의 시험 범위를 따른다.

| 검토 항목 | 내용 |
| --- | --- |
| 실제 사용자·문제 가설 | 마지막 이용자·관리자가 장비 표시·충전 구역·통로의 확인과 인계를 반복하며 누락 여부를 재확인하는가? |
| 유용한 로봇 업무 | 정한 지점의 최신 표시·외관을 가져오고, 가상 이상 신고 후 같은 항목을 재확인해 담당자의 판단·후속 요청 연결 |
| 기존 방식과의 비교 | 체크리스트·사람의 순회·고정 카메라와 같은 항목·조건에서 비교. 여러 구역·가림 때문에 추가 정보가 생기는지 확인 |
| 현재 장비의 첫 범위 | 실제로 촬영 가능한 표시 또는 인쇄·화면 모형을 방문해 원본·시각·지점·사람 판단·미확인 사유를 저장 |
| 추가 수단·검증 필요 | 실제 온도·전류·내부 상태는 별도 센서·설비 정보 필요. 표시 의미·카메라 높이·가림·촬영 허용 범위도 확인 |
| 기술·실패 지점 | 잘못된 지점·오래된 사진·표시를 읽을 수 없는 사진, 외관 확인에서 실제 전원 차단·안전 상태를 추정하는 오류 |
| 첫 작은 시험 | 이용자에게 확인 항목·누락 상황을 묻고, 선택한 한 항목을 사람이 직접 확인한 결과와 로봇 사진으로 확인한 결과를 대조 |

실습실 시험을 채택해 수행할 경우 실제 환경의 항목과 시험용 모형 항목을 각각 표시한다. 전기장치 내부 접근·의도적 과열·화염·유해 연기 없이 촬영·기록·모의 경보 흐름을 시험한다. 사용자 불편이나 이동의 추가 가치를 확인하지 못하면 다른 업무·산업 배경을 검토할 근거로 남긴다.

### 1. 물류센터·자동화 창고

| 고정 감시와의 관계 | 여러 배치의 가림·측면 확인에 이동성 활용. 특정 충전기 상시 감시와 넓은 천장 영역은 고정 설비도 함께 검토 |

| 현재 장비의 모형 범위 | 낮은 랙·상자·충전기 패널 모형 방문, RGB 증거와 시간·지점 기록. LiDAR는 해당 높이의 통행 관측에 활용 |
| 추가 장비·검증 필요 | 실제 발열은 열 센서, 높은 선반은 다른 관측 높이 확보 필요. 적재에 따른 무선·지도·가림 변화를 시험 |
| 기술·실패 지점 | 지점 ID와 사진 연결, 접근 경로·정지 자세, 작업 상태. 도착 성공인데 대상이 안 찍히는 실패에 유의 |
| 첫 작은 시험 | 같은 상자 배치에서 고정 카메라와 로봇의 관측 가능 지점을 표시하고, 배치를 바꿔 재촬영. ‘방문·판독·미관측’ 목록을 결과로 남김 |

| 기술·실패 지점 | 촬영 자세·ROI·이력 비교·재점검 요청. 이전 사진을 최신 결과로 표시하거나 계기 종류를 혼동할 위험 |
| 첫 작은 시험 | 고정 촬영과 이동 후 촬영을 같은 패널·조명·거리 조건에서 비교. 사람이 읽을 수 있는지와 재촬영 필요 사유를 라벨링 |

심화·확장 개발 때 기존 수집·원본 확인 경로와 시험 자료를 유지한다. 새 분석 결과는 알고리즘·설정·시각과 함께 별도로 저장한다. 모델 또는 추가 장비가 실패해도 기존에 완료한 방문·증거 회수·사람의 확인 업무를 계속 시연할 수 있게 검토한다.

최소 완결형의 직접 성과는 통제된 모형에서 점검 정보를 확보하고 확인 업무를 끝낸 결과다. 실제 산업 현장의 화재 발생률 감소·진압 성능·법정 점검 대체 효과는 별도 검증 과제로 기록한다.

## 기존 ①·②·③과 연결할 때의 후보

아래는 새 기능을 확정하는 표가 아니다. 기존 희망과 맞는 연결점을 제시하며 책임·배포 변경은 [06 문서](06_INTERFACES_DEPLOYMENT.md), 결정 상태는 [08 문서](08_DECISIONS_OPEN_QUESTIONS.md)에서 논의한다.

| 영역 | 사용할 수 있는 역할 | 이 조사에서 만들어 볼 작은 결과 |
| --- | --- | --- |
| ① 웹·백엔드·DB | 지점별 요청·진행·증거·담당자 확인·공식 이력 제공 | 한 요청에서 원본 사진과 확인 이력이 연결되는지 시험 |
| ② 독립 PC 앱 | 자료를 일반 폴더로 가져와 오프라인 분석·비교·설정 보존·선택 제출 | 사진의 밝기·선명도 또는 로그 수신 간격을 실제 계산하고 결과를 재열기 |
| ③ 실행·수집·통신 | 방문·정지·관측·전송·오류·재시작 시 상태 확인 | 도착 성공·촬영 성공·전송 성공을 개별 기록하고 실패 지점 추적 |
| 기존 로봇 상태 활용 | 제공되는 배터리·센서·구동 값과 수신 시각을 작업 기록에 연결 | 센서 수신 중단·오래된 상태가 발생한 작업을 사후 조사 |
| Docker Compose | 별도 PC 서버·DB 서비스의 환경 재현·재시작·데이터 보존 | 서비스 재시작 후 같은 요청·증거가 보존되는지 검사 |

PC 앱은 확보한 파일과 메타데이터를 외부 편집기·스프레드시트·코딩 에이전트에서 읽을 수 있게 구성하는 개인 희망을 유지한다. 산업 배경을 바꾸더라도 이 로컬 작업 흐름을 활용할 수 있다. 폴더의 한 사례를 수동으로 정리해 본 뒤 공통 자동화의 필요성을 판단한다. 단순 다운로드만으로 첫 분석 완료를 평가하지 않는다.

자료 필드 후보는 작업·지점·로봇 ID, 발생·촬영·수신 시각, 관측 자세, 원본 파일, 모의·실측 구분, 센서 단위·출처, 사람의 확인과 분석 버전이다. 모두를 처음부터 의무화하지 않고 업무 재현에 필요한 항목부터 시험한다. 사진의 전송 성공과 점검 대상의 정상 판정은 별도 결과로 관리한다.

업무 기록과 물리 실행의 연결은 기존 ③ 논점에 따른다. 재시작 시 작업 ID·실행 시도·완료 증거를 대조하고, 결과를 잃어 실행 여부가 불확실한 동작은 상태를 확인한 뒤 후속 조치를 정한다. 서버 응답이 없었다는 이유만으로 같은 물리 동작을 자동 반복하는 설계는 별도 검토한다. 프로그램 수·통신 방식·상주 여부는 이번에 확정하지 않는다.

### Docker가 제공하는 복구와 직접 개발할 처리

Docker의 재시작 정책은 컨테이너 종료·데몬 재시작 조건에 적용된다. Compose의 시작 의존성과 healthcheck 조건도 사용할 수 있다. 요청 중복, 파일 일부 전송, DB와 로봇 사이의 작업 상태 대조는 애플리케이션에서 설계할 책임이다. 컨테이너가 unhealthy로 표시됐다는 이유만으로 모든 업무가 자동 복구된다고 가정하지 않는다. 서버 PC 전체의 전원·디스크·네트워크 장애는 서비스 프로세스 종료와 별도 시험으로 다룬다. [Docker 재시작 정책](https://docs.docker.com/engine/containers/start-containers-automatically/), [Compose 시작 순서·건강 상태](https://docs.docker.com/compose/how-tos/startup-order/)

이번에는 모든 ROS2 노드를 컨테이너화하는 범위를 추가하지 않는다. 기존 실행 환경과 Chieftain의 주행 소스를 우선 확인하고, 필요한 서버 서비스를 대상으로 재현·보존 시험을 검토한다.

## 두 로봇을 검토할 수 있는 방법

TurtleBot3가 중심이며 JetBot MINI도 활용하는 방향을 기본 전제로 기획한다는 최신 사용자 설명을 반영한다. 보유 문서의 4GB 사양과 실제 설치·동작 결과를 구분하고, 역할·연동 방식은 팀과 구체화한다. [장비·실행 환경](06_INTERFACES_DEPLOYMENT.md#robot-environments)

| 검토안 | 비교할 가치 | 먼저 확인할 부분 |
| --- | --- | --- |
| 같은 지점의 다른 각도 관측 | 첫 사진에서 가린 항목이 추가로 보이는가? | 실제 카메라 시야·제어·접근 자세 |
| 다른 지점의 관측 | 한 로봇 대비 확인 지연이 줄어드는가? | 이동 가능 범위·통로 충돌·작업 배정 |
| 촬영·확인 요청의 인계 | 자료와 지점이 정확히 이어지는가? | 공통 ID·시간·실행 결과·통신 제약 |

두 로봇의 센서·프로토콜이 다르면 필요한 기능만 로봇별 연결부로 감싸는 방안을 비교할 수 있다. 공통 업무 기록은 맞추되 제공되지 않는 센서 필드를 억지로 채우지 않는다. ROS2 공통화와 개별 제어 API를 쓰는 방식 중 실제 지원 범위·구현 부담·오류 확인성을 시험한 뒤 선택한다.

JetBot 세팅과 각 모듈의 독립 시험을 병행할 수 있다. 두 로봇을 연결하기 전후의 결과를 각각 기록해 첫 업무의 완결성과 두 번째 로봇이 추가한 관측·업무 가치를 함께 확인한다.

## 주제 선택 전에 할 작은 시험

아래 순서는 의존 관계를 고려한 제안이다. 일정·개발 기간·합격 수치를 임의로 정하지 않는다. 수치 기준은 첫 결과를 본 뒤 팀이 목표 업무에 맞게 시험 전에 정하고, 평가 도중에 편의상 바꾸지 않는다.

| 시험 | 방법 | 남겨야 할 결과 | 판단할 질문 |
| --- | --- | --- | --- |
| 장비 능력 확인 | 로봇별 모델·OS·제어·영상·상태 조회를 실제 확인 | 지원 기능·미지원·오류·미시험 목록 | 어떤 관측을 어느 장비로 시험할 수 있는가? |
| 촬영 가능성 | 대표 배경 2~3개에 해당하는 패널·상자를 같은 조건으로 촬영 | 원본·거리·높이·조명·가림·사람의 판독 | 대상을 실제 카메라 높이에서 읽을 수 있는가? |
| 이동 관측의 추가 가치 | 고정 카메라 배치 근거를 적고 같은 표적·배치에서 이동 촬영 | 관측 가능한 지점·누락 면·소요 시간·설치 조건 | 추가 정보가 필요한 업무인가? |
| 첫 요청 완결 | 지점 한 곳 요청 → 이동 → 사진 → 저장 → 사람 확인 | 요청 ID·원본·상태 이력·실패 사유 | 관리자가 현장을 직접 다시 가야만 확인되는가? |
| 재촬영 개선 | 사전에 정한 밝기·흔들림·가림 조건에서 단일 촬영과 재촬영 비교 | 판독 가능률·잘못 수용한 사진·재시도·시간 | 다시 찍는 비용 대비 판단 가능한 자료가 늘어나는가? |
| 가상 경보 연결 | 모의 센서 값·경보 ID·발생 시각을 주입 | 모의 표기·경보와 관측의 연결·지연 기록 | 다른 지점이나 오래된 경보와 혼동하는가? |
| 통신·프로세스 오류 | 파일 전송 중 연결 중단, 중복 요청, 서비스 프로세스 재시작 | 보존 파일·작업 상태·중복·미완료 처리 | 무엇을 완료로 보고 다시 확인해야 하는가? |
| PC 로컬 분석 | 한 작업을 폴더로 가져와 실제 계산·저장 후 오프라인 재열기 | 입력·설정·결과·메타데이터·재현 기록 | 다른 사람이 같은 근거를 다시 볼 수 있는가? |
| 추가 센서 채택 판단 | 구매·대여 전 측정 대상·출력·단위·SDK·판독 위치 조사 | 장비 후보 명세와 미확인 항목 | 필요한 물리량을 실제로 제공하는가? |
| 두 로봇 비교 | 각각 단독으로 확인한 뒤 같은 모형 업무에서 연결 시험 | 단독·협업의 관측 범위·지연·연결 오류 | 추가 장비가 제공하는 독립적인 가치가 있는가? |

주행 중 통신 장애 시험은 먼저 정지 상태나 모의 실행으로 상태 처리부터 검증한다. 실제 이동 시험으로 확대할 때는 실험 공간·정지 수단·작업자 동선을 확인한다. 서버 PC 전체 장애 시험은 저장·업무 복구 설계를 검토한 뒤 팀이 범위를 정한다.

### 측정과 정답의 정의

- **관측 성공**은 정해진 지점·대상·시각의 원본이 확보됐는지 판단한다. 이동 성공만으로 계산하지 않는다.
- **판독 가능**은 사람이 정해진 질문에 답할 수 있는지 사전 기준으로 표시한다. ‘사진 있음’과 구별한다.
- **판정 성능**은 미리 설정한 모형의 정답과 비교한다. 정상·이상·확인 불가, 오탐·미탐을 함께 기록한다.
- **업무 완결**은 담당자가 확인·후속 확인 요청·확인 불가 중 하나를 근거와 함께 남겼는지 살핀다.
- **수행 시간**은 요청·이동·촬영·확인에 사용한 시간과 사람의 실제 개입을 구분한다.
- **개선 비교**는 표적·배치·조명·통로·시험 회차를 맞추고 실패 회차를 포함한다.
- **ML 평가**는 같은 연속 촬영 프레임을 무작위로 나누는 방식의 누출에 유의한다. 수집 회차·날짜·배치 등 독립 조건으로 학습·평가를 나눌 수 있는지 확인한다.
- **화재 예방 효과**는 모형 시험의 판독률·방문 시간과 별도의 주장이다. 실제 화재를 막았다는 결론은 생성하지 않는다.

실제 산업 담당자를 만나지 못했다면 모형 요구와 평가자는 팀이 정했다는 사실을 명시한다. 사용자를 확인한 뒤 반복 업무의 빈도·기존 방식·실패 비용을 보완한다.

## 기술 도입의 비용을 판단할 근거

| 기술·기능 후보 | 먼저 확보할 근거 | 확장 판단 |
| --- | --- | --- |
| Python·OpenCV | 촬영 가능한 자료와 사람이 정한 판독 기준 | 품질·ROI 분석이 확인 업무를 개선하면 채택 |
| 전통 ML | 규칙 기준, 특징·라벨·독립 시험 회차 | 규칙과 같은 평가 자료에서 개선 여부 확인 |
| PyTorch 등 | 영상·라벨·평가 환경과 기준 방법 | 모델 실패 시 기존 원본 확인 업무 유지 |
| 열화상·가스 | 대상 물리량·장비 출력·교정·설치 조건 | 추가 관측이 필요한지와 데이터를 얻는지부터 판단 |
| 고급 주행·재계획 | 기존 주행의 실패 로그·목표 지점·동작 범위 | Chieftain의 코드로 해결되는지 먼저 확인하고 개선 필요를 정의 |
| 서보모터 기반 모형 투척 | 저렴한 서보모터의 투석기형 장치 등 별도 후보, 팀 채택·비위험성 표적·시험 공간 | 도달·실행 검증을 점검 업무와 별도 평가 |
| 다중 로봇 | 각 장비의 단독 지원 기능과 관측 결과 | 지연·가림·업무 분담 개선과 연결 부담 비교 |

로봇팔과 목 구동 안건은 함께 잠정 폐기 상태로 반영한다. 위 모형 투척 후보의 필요성·기구 검증은 별도로 논의한다.

## 회의에서 탐색하고 이후 확인할 사항

1. 첫 사용자의 확인 질문과 후속 행동을 정하고 실습실 자체 업무·산업 모형 중 무엇을 검토할지 탐색한다.
2. 실습실을 포함한 11개 후보에서 비교해 보고 싶은 배경·업무를 탐색한다. 촬영 시험 범위는 실제 준비 상황에 맞춰 선택한다.
3. 실제 열·가스 감지를 목표에 넣을지, 모의 경보·RGB 증거 확인을 첫 범위로 둘지 논의한다.
4. 제어·센서·카메라의 실제 지원을 확인한 뒤 두 로봇 참여 방법을 정한다.
5. 사람의 확인을 포함한 첫 완료 기준, 데이터의 공식 기록 위치, PC 로컬 결과 제출 범위를 논의한다.
6. 실험 공간·기간·인원·담당·예산·현장 인터뷰 가능성을 확인한다.

현재는 검증할 질문과 대안을 마련한 상태다. 모형화가 가능한 배경을 실제 현장 투입 가능성으로 확대하지 않는다. 산업별 난이도·예상 정확도·완료 기간은 시험 근거가 확보되기 전까지 확정하지 않는다.

외부 기술 문서는 2026-11-14 열람했다. 산업 10개의 조사 근거는 유지하고 실습실 자체의 PBL 검토를 추가했다. 프로그램 책임·로봇 임무·기술 스택은 팀 미결정이며, 논의 시점은 [08 문서](08_DECISIONS_OPEN_QUESTIONS.md#meeting-topics)를 따른다.
