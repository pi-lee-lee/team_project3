# ③ 시스템·통신 소프트웨어

## 개인 희망과 범위

실제 로봇 작업 실행·장치 연동·센서 수집·통신·오류 처리·복구를 개발해 보고 싶은 영역이다. 여러 모듈·프로그램이 서버·로봇·클라이언트 PC에 나뉠 가능성을 열어 둔다. 실행 위치와 분리는 [06 문서](06_INTERFACES_DEPLOYMENT.md)에서 비교한다.

## ①과 나눌 기록의 의미

분석자는 다음 책임 배치를 제안한다.

- ①은 요청·배정·취소 의도, 공식 확인·조치와 공유 이력을 관리한다.
- ③은 실제 장치 접수·이동·촬영·실행 사건을 원본 응답과 함께 기록한다.
- 단절 뒤에는 작업·명령·시도·관측 ID와 순서·버전을 대조한다. 기록된 사실의 종류에 따라 처리한다.
- 촬영 완료·전송 대기·사람 확인 전은 함께 성립할 수 있는 상태다.
- 타임아웃이면 실행 결과를 조회하고 불명확성을 남긴다. 물리 동작과 DB 기록 사이의 중단을 다룬다.

관측 재전송은 같은 관측을 다시 전달하는 일이다. 재촬영·투척 재실행은 새 물리 동작이므로 확인 정책이 필요하다. ID 처리만으로 전원 중단까지 포함한 정확히 한 번의 물리 실행을 보장할 근거는 없다.

## 로봇별 연동과 상태값

공통 업무 요청을 로봇별 검증된 인터페이스에 연결하는 방식을 후보로 둔다. 두 로봇 모두 같은 토픽·자율주행·완료 응답을 제공한다고 가정하지 않는다. 지원 여부·유효성·단위·시각·버전을 함께 전달한다.

배터리·엔코더·Odometry·IMU·LiDAR·구동 관련 값은 현재 설치 환경에서 확인해야 한다. 공개 메시지 필드의 존재와 실제 반환 가능성을 대조한다. 하드웨어 상태를 활용하는 응용 SW 성과로 기록하고, OpenCR 펌웨어 개발 경험은 실제 수정·검증 범위에 따라 판단한다.

## ②와의 경계

PC 앱 내부 다운로드·로컬 분석·업로드도 통신과 작업 실행을 포함한다. 이를 모두 ③의 별도 서비스로 옮길 필요는 없다. 종료 후 지속성, 장치 접근, 부하·장애 격리가 필요한지 확인한 뒤 분리한다.

조종 화면의 위치와 실제 제어 경로는 별도 결정한다. 여러 화면이 요청을 내더라도 제어권·운영/시험 모드·늦은 명령 처리 기준을 합의한다.

## 남길 수 있는 첫 성과

기능을 채택할 경우 한 요청의 실제 관측 보고와 선택한 통신 장애에서의 자료 보존·회수를 첫 목표로 제안한다. 구현·시험을 수행한 뒤 실제 장애 조건·실행 위치·결과를 기록할 수 있다. 상태 수집과 사용자 업무 완료의 차이도 평가할 항목이다. 현재 이 문서는 구현·시험 결과 보고가 아니다.

상세 근거는 [책임 분석의 상태·복구](research/feature_responsibility_analysis_2026-11-13.md#states)에서 본다.
