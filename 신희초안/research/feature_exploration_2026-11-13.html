실패한 점검을 조사하는 PC 도구

“왜 실패했는지 터미널 여러 개를 뒤지는 시간을 줄일 수 있을까?”

작업을 선택하면 이동 요청·도착·촬영·전송 실패가 시간 순서대로 나타난다. 해당 시점의 사진과 배터리 전압, 카메라·LiDAR의 최근 수신 상태를 함께 조회한다. 담당자는 확인한 사실과 추정 원인을 구분해 메모하고 자료 묶음을 저장한다.

첫 완성은 저장된 한 작업을 열어 사진·이벤트·몇 개의 수치 기록을 함께 보고 내보내는 것이다. 이후 실시간 수신, 시간 구간 탐색, 시험 회차 비교, 판정 기준 조정을 추가할 수 있다.

직접 책임질 내용은 자료 읽기·검증, 작업과 시각의 연결, 화면 탐색, 그래프, 오류 표시, 내보내기, 시험 사례다. 원인 분석을 돕는 관측을 제공하고 원인을 자동 확정하는 기능은 별도 검증한다.

비교 실험은 같은 기록에서 특정 오류 발생 지점·누락 항목을 찾는 과제를 주고 수동 로그 조회와 도구 사용을 비교하는 것이다. 정확히 찾았는지와 조사 시간을 함께 기록한다. 서로 다른 PC 시각을 섞으면 오차가 생기므로 첫 범위는 동일 수집기의 수신 시각을 기준으로 맞추고 원본 시각도 보존하는 방법을 검토한다.

서버 장애 뒤에도 점검 결과를 회수하는 기능

촬영 결과를 로컬에 보관하고 서버가 수신을 확인할 때까지 전송 대기로 관리한다. 서버가 돌아오면 보관 자료를 보내고 같은 관측이 여러 번 도착한 상황을 처리한다. 웹에는 마지막 확인 상태와 전송 대기 항목을 표시한다.

첫 완성은 주행 연결이 유지되는 조건에서 서버 API 장애를 재현하고, 이미 확보한 사진·기록이 복구 후 누락·중복 없이 등록되는지 확인하는 것이다. 이후 실행 프로그램 재시작, 일부 파일 업로드 실패, 늦은 응답·취소와의 충돌을 확장 시험으로 둔다.

직접 책임질 내용은 관측 ID·시도 ID, 로컬 저장, 확인 응답, 재시도 간격, 서버 중복 처리, 처리 이력과 시험 프로그램이다. 웹 API와 실행 프로그램이 함께 필요할 수 있다.

비교 실험은 장애를 넣기 전후에 예상 관측 목록과 실제 등록 목록, 사진 파일, 처리 상태를 대조하는 것이다. 사진 복구와 새로운 주행·투척의 재실행 정책은 별도로 정한다.

첫 완성은 촬영한 자료를 사람이 검토하고 제한된 모형 표시의 기본 규칙을 평가하는 도구다. 이후 자동 재촬영 제안, 실제 재촬영 효과 비교, 특징 기반 분류 모델을 추가할 수 있다.

직접 책임질 내용은 ROI·특징 계산, 기준 저장·버전, 자료·정답 관리, 일괄 판정, 오판 조회와 비교 그래프다. 장비 표시의 의미와 사진 품질은 각각 라벨과 평가 기준을 정한다.

비교 실험은 정상 촬영·어두움·흐림·가림 등 조건을 바꾸고, 기준 적용 전후의 판독 가능률과 불필요한 재촬영·놓친 불량 사진을 비교하는 것이다. 사전에 정확도나 필요한 자료 수를 확정하지 않는다.

ML을 추가하면 같은 자료에서 기본 규칙과 비교한다. 사람이 읽을 수 있는 사진을 불필요하게 다시 찍게 하는 경우, 읽기 어려운 사진을 통과시키는 경우를 각각 조사한다. 촬영 구역과 조명·대상을 넓힐수록 새로운 자료가 필요하다. 일반적인 사진 품질 문제의 난도는 실제 장면에 따라 달라진다.

같은 촬영 회차의 연속 프레임을 학습과 평가에 섞으면 실제 새 장면의 성능을 과대평가할 수 있다. 촬영 회차·날짜·대상 등 의미 있는 그룹을 정하고 분리하는 방식을 검토한다. scikit-learn은 데이터 누출 방지와 그룹을 겹치지 않게 나누는 GroupKFold를 공식 문서에서 설명한다. scikit-learn 데이터 누출 안내 · GroupKFold

필요한 표본 수와 목표 성능은 현재 결정할 근거가 부족하다. 먼저 독립된 촬영 조건에서 라벨을 붙일 수 있는지와 기본 규칙의 오류를 확인한다. ML 모델이 유용해지기 전에도 사진 검토·보정·재촬영 요청 기능이 업무 성과를 제공하도록 구성한다.

팀 회의에 가져갈 개인 희망 목록 초안

아래 문장은 대화와 이번 조사에 근거해 작성한 추천 초안이다. 사용자가 모두 직접 맡겠다고 결정한 목록으로 취급하지 않는다. 특히 끌리는 항목과 더 알아보고 싶은 항목을 고르는 용도로 사용할 수 있다.

저는 로봇을 이용한 점검 과정에서 아래 기능들을 만들어 보고 싶습니다.

  1. 요청부터 확인까지 끝나는 점검 업무를 만들고 싶습니다. 장소를 선택하면 실제 이동·촬영 결과가 저장되고, 담당자가 확인이나 재점검 요청을 남길 수 있으면 좋겠습니다.
  2. 실패한 작업을 조사하는 독립 PC 앱을 만들고 싶습니다. 그때의 사진·로봇 상태·통신 기록을 같은 작업에서 찾아볼 수 있으면 좋겠습니다.
  3. 센서 값의 최근 갱신 여부와 출발 준비 상태를 확인하고 싶습니다. 실제 지원되는 값으로 판단하고 이유를 보여 주고 싶습니다.
  4. 서버가 끊겨도 사진과 기록을 보존하고 복구 후 전달하는 기능을 구현해 보고 싶습니다.
  5. 중복 명령·타임아웃·취소를 처리하는 작업 프로그램을 만들어 보고 싶습니다. 투척은 수신·실행·결과 확인을 구분해 보고 싶습니다.
  6. 실제 기록을 다시 열어 오류를 재현하고 조사하는 기능을 만들고 싶습니다. 팀원에게 진단 자료도 전달할 수 있으면 좋겠습니다.
  7. 사진의 관심 영역과 판정 기준을 조정하고 비교해 보고 싶습니다. 흐림·어두움 때문에 재촬영이 필요한 상황도 다뤄 보고 싶습니다.
  8. 모형 투척의 조건과 결과를 기록·분석하고 싶습니다. 기구가 동작하면 거리·방향 보정 효과까지 비교해 보고 싶습니다.
  9. Docker Compose로 서비스를 재현하고 재시작·데이터 보존을 시험하고 싶습니다. 가능하면 이 시험을 반복 실행하도록 만들고 싶습니다.
  10. JetBot MINI의 세팅이 성공하면 실제 가능한 입력·제어를 확인해 팀 프로젝트에 연결하고 싶습니다. 맡길 임무는 기능과 장비를 확인하며 정하고 싶습니다.

프로젝트의 PBL 문제는 팀에서 구체화하고, 웹·PC 앱·시스템 통신·로봇 상태 활용·Docker가 각각 어떤 문제 해결에 기여할지 기능과 함께 검토한다. 개인의 우선 관심 묶음으로는 ‘PC 진단과 기록 재검토’, ‘통신 장애 후 결과 회수’, ‘사진 보정·평가’를 제안한다. 투척 시험 도구도 실제 기구가 준비되면 독립적인 후보가 된다.

생각을 구체화하는 작은 활동

먼저 관심 기능 하나의 화면을 종이에 그려 본다. ‘사진과 실패 시각을 누르면 무엇이 보여야 할까’를 적거나, 같은 장소의 두 사진을 비교하면서 필요한 버튼과 정보를 적어도 된다.

그다음 실제 자료 하나로 기능의 의미를 확인한다. 사진 검토를 고르면 서로 다른 촬영 조건의 사진을 보고 판독 가능 여부를 기록한다. 진단을 고르면 한 번의 시험에서 필요한 사건·센서·설정을 적는다. 투척을 고르면 기구 담당자와 함께 시험 조건과 결과 기록 양식을 정한다. 자료 확보가 어려운 부분은 미확인으로 남긴다.

마지막으로 각 기능에 세 문장을 붙인다.

  1. 누가 어떤 상황에서 이 기능을 쓰는가.
  2. 입력으로 무엇을 받아 어떤 결과를 제공하는가.
  3. 어떤 시험을 통과하면 작게 완성됐다고 말할 수 있는가.

예를 들어 ‘사진 보정 도구’를 골랐다면, 담당자가 확인하기 어려운 점검 사진을 검토하고, 사진·관심 영역·기준값으로 판정과 재촬영 후보를 제공하며, 별도 촬영 자료에서 사람의 평가와 오류를 대조하는 것까지를 첫 범위로 적을 수 있다. 화면과 자료를 구체화하며 실행 위치와 책임을 정할 근거도 얻는다.

출처와 확인 범위

조사는 로봇 점검 운영 제품의 공식 설명, 진단 도구 문서, Nav2 Humble·rosbag2·TurtleBot3 메시지의 공식 소스, Docker·OpenCV·scikit-learn 문서, 요청 재시도에 관한 AWS 기술 글을 중심으로 수행했다. 일부 ROS 문서 페이지는 접근 제한이 있어 공식 GitHub 저장소와 Humble 소스를 참고했다.
