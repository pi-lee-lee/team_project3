# TurtleBot3 기반 실습실 원격 점검 및 로봇 진단 시스템

ChatGPT·Codex 제안 통합안 · 2026년 11월 13일 · 팀 첫 회의용 검토 자료

## 팀원에게 설명할 쉬운 시나리오

**나는 ‘실습실 퇴실 점검 로봇’을 생각했어.** 수업이 끝나면 담당자가 여러 장소의 장비를 돌아다니면서 표시등이나 화면을 확인하고 기록해야 하잖아.

관리자가 점검을 요청하면 터틀봇이 정해진 장소를 방문해서 장비 사진을 찍어 오는 거야. 담당자는 자리에서 사진과 촬영 시각을 보고 상태를 확인할 수 있어.

사진이 흐리거나 가려졌으면 그 사진을 살펴보고 다시 찍도록 요청해. 로봇이 도착하지 못했거나 사진이 안 왔으면 현장 담당자가 PC 프로그램에서 로봇 상태와 통신 기록을 확인하는 거지. **어느 경우든 마지막에는 같은 점검 기록에 확인한 결과와 추가 조치가 필요한 항목을 모아 주는 거야.**

처음에는 두 장소를 방문해 최신 사진과 결과를 제공하는 것까지 완성하고 싶어. 그다음 PC 진단과 오류 처리를 갖추고, 여력이 생기면 표시등 자동 판정이나 재촬영 방법을 비교해 보는 거야.

실습실 퇴실 점검을 가정한 제안이다. 실제 이용자·점검 장비·필요한 확인 항목은 팀과 현장에서 구체화한다.

## 2. 하나로 합친 PBL 문제

### 누구의 어떤 문제인가

시설·실습실 관리자는 흩어진 장비의 표시 상태를 반복 확인해야 한다. 직접 방문과 기록에는 시간이 들고, 이전 점검 기록이 현재 상태를 보여 주는지 확인하기 어렵다. 로봇이 사진을 가져오더라도 사진이 흐리거나 입력·전송에 문제가 생기면 해당 점검을 다시 확인해야 한다.

**핵심 질문은 관리자가 직접 방문하지 않고 최신 관측을 확보하며, 확인이 어려운 항목을 근거와 함께 후속 조치로 연결할 수 있는가다.**

관측한 장비의 표시 의미와 정상·이상 기준은 대상별로 정의한다. 첫 실험에는 상태를 직접 바꿀 수 있는 모형 패널을 사용할 수 있다. 보고서에는 관측한 표시 상태, 사람의 판단, 판단이 어려운 이유를 남긴다.

### 이동 로봇이 필요한 조건

여러 위치에 접근해 가까이서 봐야 하는 표시 영역이 있고, 로봇 카메라 높이에서 실제 촬영이 가능해야 한다. 직접 방문과 고정 카메라로 같은 확인 업무를 수행하는 조건도 비교한다. 이동형 방식의 효용은 장소 분산·시야·설치 부담·사람의 개입 시간으로 검토한다.

로봇이 접근하기 어려운 장비나 촬영 범위 밖의 상태는 점검 대상과 관측 범위에 명시한다. 실험실 모형에서 확인한 성과와 실제 시설 적용 성과를 각각 기록한다.

## 3. 공통 업무에서 시작해 두 확인 과정이 다시 만나는 흐름

```text
공통 업무
점검 요청 → 준비 확인 → 이동·촬영 → 관측과 상태 기록

다음 확인 과정으로 이어짐
  • 사진을 확인하기 어려움
    사진 검토 → 재촬영·현장 확인 요청
    심화 시 품질 검사·판정 보정

  • 이동·입력·전송에 문제
    로봇·통신 진단 → 복구·현재 상태 확인
    재전송 또는 새 관측 시도

두 과정이 같은 점검 항목으로 연결
유효한 관측 확인 → 결과·근거·남은 조치를 하나의 보고서에 기록
```

### 공통 업무

관리자가 웹에서 점검 지점을 선택한다. 시스템은 해당 단계에서 지원하는 준비 상태를 확인하고 이동을 요청한다. 도착 결과를 확인한 뒤 새 사진을 촬영하고 장소·시각·작업 ID와 함께 저장한다. 관리자는 유효한 사진을 보고 장비 상태를 확인한다.

### 사진으로 상태를 확인하기 어려운 경우

로봇은 장비 앞에 도착했고 사진도 저장됐지만, 반사·흐림·가림 때문에 표시를 읽기 어렵다. 담당자는 PC 앱에서 해당 관측 사진을 확대하고 같은 장비의 이전 자료와 비교한다. 필요하면 사전 등록한 위치에서 재촬영을 요청하거나 현장 확인을 지정한다.

새 사진을 확보하면 원래 점검 항목에 재관측으로 연결한다. 담당자가 확인할 수 있으면 결과를 기록하고, 끝내 확인하기 어려우면 그 이유와 현장 확인 요청을 남긴다. 이후 OpenCV를 도입하면 같은 사진 검토 과정에 품질 검사와 판정 기준 보정을 추가할 수 있다.

### 로봇·입력·통신 문제로 관측을 확보하지 못한 경우

로봇이 도착하지 못했거나, 카메라 입력이 오래됐거나, 서버에서 사진을 받지 못했다. 현장 담당자는 PC 앱에서 해당 작업 시점의 배터리·센서 수신·이동 결과·통신 이력을 살펴본다. 도구는 확인한 사실과 오류 시각을 제시하고, 담당자가 원인을 조사한다.

서버 전송 문제라면 로컬에 보존한 사진과 기록을 재전송한다. 촬영이나 이동을 다시 해야 한다면 현재 상태를 확인하고 새 시도로 요청한다. 전송이 복구되면 확보한 사진의 판독을 이어가고, 해결되지 않으면 미확인 사유와 후속 조치를 남긴다.

### 다시 만나는 지점

**두 과정 모두 같은 작업 ID와 점검 항목으로 돌아와 최종 보고서를 구성한다.** 보고서는 무엇을 관측했고 누가 확인했는지, 재촬영·진단이 왜 필요했는지, 아직 어떤 조치가 필요한지 보여 준다.

한 작업에서 사진 문제와 통신 문제가 함께 생길 수도 있다. 입력·촬영·전송의 유효성을 확인한 뒤 해당 사진의 내용을 판단한다. 재관측은 새 관측 ID로, 사진 재전송은 같은 관측 ID로 기록해 이력을 이어간다.

## 4. 팀원에게 보여 줄 두 가지 상황

### 상황 A — 표시창이 가려진 장비

1. 관리자가 두 장비의 점검을 요청한다.
2. 첫 장비는 사진으로 표시를 확인한다. 두 번째 장비는 표시창이 가려져 확인이 어렵다.
3. 담당자가 두 번째 장비를 확인 필요로 기록하고 PC 앱에서 사진을 검토한다.
4. 가림을 제거한 시험 조건에서 같은 장비를 다시 촬영한다.
5. 최초 사진과 재관측 사진, 확인 결과가 하나의 보고서에 연결된다.

시연에서는 첫 관측 실패가 사라지지 않고 개선 전후의 근거로 남는 모습을 보여 준다. 재촬영 요청의 자동화는 후속 단계에서 비교한다.

### 상황 B — 사진은 찍었지만 서버 응답이 사라진 경우

1. 로봇은 관측을 수행하고 로컬에 사진과 이벤트를 저장한다.
2. 시험용 서버 API의 응답을 유실시키거나 서비스를 재시작한다.
3. 웹에는 마지막 확인 상태와 전송 대기·연결 확인 필요를 표시한다.
4. PC 앱에서 관측 파일의 저장과 전송 이력을 살펴본다.
5. 복구 후 같은 관측을 재전송하고, 보고서에서 중복 없이 사진과 결과를 확인한다.

이 시험은 로봇 주행 연결이 유지되는 조건에서 서버 경로의 장애를 재현한다. 로봇 무선망 장애는 별도 조건에서 정지·취소·현재 상태 확인까지 시험한다.

### PC 앱은 한 개로 구성

PC 앱의 기본 메뉴를 ‘로봇·통신 진단’과 ‘관측 자료 검토’로 제안한다. 공통 진입점은 작업 ID와 점검 항목이다. 진단 메뉴에서 입력·상태·오류 이력을 살피고, 자료 검토 메뉴에서 사진·촬영 시각·재관측을 살핀다. 두 메뉴는 같은 작업 시점을 따라간다.

사진 판독을 자동화하는 단계에서는 자료 검토 메뉴에 ROI 선택·기준값 조정·일괄 재판독·정답 대조를 추가한다. 실제 점검과 PC 재판독이 같은 기준 버전과 판정 로직을 사용하도록 연결한다. 웹은 관리자의 요청·확인·기록 업무를 맡는다.

### 프로세스와 기술 선택

ROS2 작업 관리자와 시스템·통신 모듈은 책임 단위다. 팀 여력에 따라 하나의 백그라운드 프로세스 안에 구현할 수 있다. 실행 위치는 로봇과 PC의 영상 처리 부하·네트워크 시험으로 정한다. 하드웨어와 연결된 ROS2 환경은 먼저 검증하고, 별도 PC의 서버·DB를 Compose로 구성한다.

C++·ROS2는 임무·통신·판정 모듈의 구현 후보이고, Python GUI는 PC 앱의 후보이다. 백엔드·웹·DB는 팀 경험과 직무 목표에 따라 선택한다. 언어·프레임워크별 학습과 시험 부담을 첫 완성 범위와 함께 산정한다.

Nav2·드라이버·ROS2가 제공하는 이동·센서 발행·통신 기능을 활용한다. 팀은 점검 업무, 사진과 작업의 연결, 진단 도구, 상태·재시도 정책, 시험을 구현한다. [Nav2 Humble 공식 문서](https://api.nav2.org/nav2-humble/html/md_nav2_simple_commander_README.html)

## 6. 단계별 완결성과 완료 조건

### 준비 시험 — 첫 범위를 정하기

실제 두 지점 이동·정지·촬영을 시험한다. 카메라 높이·조명·가림 조건에서 표시 영역이 보이는지 확인한다. 설치 환경의 배터리·필수 센서·구동 관련 데이터 제공 여부와 갱신 상태를 확인한다. 이 결과로 대상과 관측 위치를 정한다.

### 산 중턱 1 — 원격 점검 최소 완결형

**웹 요청 → 실제 이동 → 새 사진 촬영 → 저장·조회 → 사람의 확인 결과 기록**을 연결한다. 정상 관측과 실패 관측을 모두 보고할 수 있어야 한다.

완료 기준은 사진과 장비·작업·시각의 연결이 맞고, 관리자가 사진을 확인해 결과나 현장 확인 요청을 남길 수 있으며, 이동·촬영 실패 사유를 조회할 수 있는 것이다. 최신 상태를 확인하는 데 실제 도움이 되는지 이용자와 시험한다.

이 단계에서 직접 방문을 줄일 수 있는 원격 관측 업무가 성립한다. 첫 범위는 제한된 두 지점과 모형 장비로 제안한다.

### 산 중턱 2 — 다섯 필수 영역을 갖춘 목표 완결형

독립 PC 앱, 지원되는 로봇 상태값의 준비 판단·진단 활용, 기본 통신 오류 처리와 재전송·중복 처리, Docker 운영을 연결한다. 담당자가 수동으로 사진을 검토하고 재점검을 요청하는 흐름도 제공한다.

완료 기준은 두 상황 A·B가 같은 작업 이력과 보고서로 이어지고, 실패 근거와 후속 조치를 추적할 수 있으며, 서버 재시작 후 기록과 사진의 연결을 확인할 수 있는 것이다. PC 앱에서 검사·자료 검토·진단 결과 저장을 실제로 수행한다.

**여기까지가 3순위의 웹·PC 앱·시스템 통신·상태값 활용·Docker를 모두 갖춘 목표다.** 실제 개발은 각 기능의 정상 흐름과 오류 시험을 묶어 작은 단위로 진행한다.

### 정상 — 관측·판단의 선택적 심화

OpenCV로 사진 품질 검사와 제한된 표시 상태 판정을 구현하고, 단일 촬영과 재촬영 정책을 비교한다. PC 앱에서 판정 기준을 보정하고 동일 자료에 대해 버전별 결과를 비교한다.

데이터와 정답이 확보되면 특징 기반 scikit-learn 분류, 숫자 표시 판독, PyTorch·TensorFlow, 추가 관측 위치 선택을 각각 검토한다. 새 모델·정책을 검증한 뒤 업무에 적용하고 기존 사진 확인과 수동 재점검 기능도 사용할 수 있게 한다.

자동 판정 결과에는 기준·모델 버전과 근거 사진을 연결한다. 사람의 최종 확인과 자동 제안의 작성 주체를 기록한다.

## 7. 작업 이력과 오류를 구현하는 기준

| 기록 | 필요한 내용과 사용 목적 |
| --- | --- |
| 작업 | 요청자·대상·기준 버전·실행 상태를 연결한다. |
| 점검 항목·관측 | 장소와 장비, 관측 ID, 촬영 시각, 사진 파일, 수집·전송 상태를 남긴다. 재촬영은 새 관측으로 연결한다. |
| 확인 결과 | 확인자 또는 판정 모듈, 정상 표시·이상 표시·확인 필요, 근거 관측을 기록한다. |
| 진단·조치 | 검사 항목·입력 상태·오류 시각·담당자 판단·재시도·현장 확인 요청을 남긴다. |
| 최종 보고서 | 항목별 확인 결과, 최초·재관측, 진단·남은 조치를 한 작업에서 조회한다. |

### 수집 상태와 장비 확인 결과

이동 도착, 촬영 성공, 전송 대기·완료 같은 실행 상태와 장비의 표시 판독 결과를 각각 저장한다. 화면에는 사진을 확인한 사람과 확인 시각을 제공한다. 전송 중인 사진이나 오래된 입력을 현재 확인 결과로 제시하지 않도록 처리한다.

### 재시도와 상태 일관성

관측 이벤트에 고유 ID를 부여하고 서버에서 중복 수신을 처리한다. 선택한 사진과 메타데이터의 로컬 저장 순서·재전송 상태를 구현한다. 서버가 저장한 뒤 응답이 유실되는 경우도 시험한다.

전송 재시도는 이미 확보한 관측의 업로드를 이어간다. 물리적 이동·촬영을 다시 수행할 때는 현재 실행 상태를 확인하고 새 시도를 기록한다. 프로세스 재시작 뒤 상태가 불명확하면 담당자에게 확인 필요를 보여 준다.

### 상태값과 진단 범위

처음에는 유효한 배터리 값과 필요한 입력의 최근 수신을 활용한다. 지원되는 엔코더·바퀴·IMU 기록을 추가할 때는 실제 의미와 단위, 관측 가능한 범위를 검증한다. 구체적인 준비 기준은 장비와 사전 시험을 바탕으로 정한다.

Humble 공식 소스에는 battery_state·imu·sensor_state·joint_states 발행 구성이 있다. 실제 설치 버전의 지원·갱신·유효성을 확인한다. 포트폴리오에는 하드웨어 상태 조회·활용과 직접 구현한 진단 범위를 명시한다. [ROBOTIS 공식 발행 구성](https://raw.githubusercontent.com/ROBOTIS-GIT/turtlebot3/humble/turtlebot3_node/src/turtlebot3.cpp)

추가 STM32 보드 구현과 OpenCR 펌웨어 변경은 현재 계획에서 제외되어 있다. 로봇 무선망과 서버 경로의 장애는 각각 시험하고, 정지·취소·마지막 확인 상태의 표시를 실장비에서 검증한다.

## 8. 비교 실험과 시연에서 남길 증거

| 질문 | 비교·시험 조건 | 측정·판단할 것 |
| --- | --- | --- |
| 원격 점검이 실제 업무에 도움이 되는가 | 같은 지점과 확인 항목에 대해 직접 방문과 원격 관측을 비교 | 전체 시간·사람의 개입 시간·누락·판독 가능한 자료·남은 현장 확인을 함께 기록한다. |
| 준비 검사가 불필요한 출발을 줄이는가 | 알려진 입력 누락·오래된 상태를 기록 재생 또는 시험 경로에 주입 | 문제 작업 시작, 정상 작업의 잘못된 보류, 미확인 상태 표시를 대조한다. |
| 기록을 신뢰할 수 있는가 | API 응답 유실·지연·서버 재시작 | 중복·유실·복구 시간·사진 연결·최종 상태를 이벤트 기록과 대조한다. |
| 재확인이 도움이 되는가 | 동일 표시·조명·가림 조건에서 단일 관측과 재관측 비교 | 판독 가능률·소요 시간·재촬영·사람의 후속 확인 건수를 측정한다. 자동 판정은 오판도 대조한다. |

실제 시험 전에는 성능 수치를 채우지 않는다. 모형 장비의 정답 상태와 물리적 조건은 시험 담당자가 별도로 기록한다. ML을 선택하면 촬영 회차·장소·조건을 고려해 학습과 최종 평가 자료를 나누고 규칙 기반 방법과 비교한다.

### 중간 보고에서 보여 줄 것

첫 보고에는 실제 두 지점의 사진과 관리자 확인 결과를 보여 준다. 목표 완결형 보고에는 가림 상황과 서버 장애 상황을 재현하고, 두 경우가 동일 보고서에 어떻게 연결되는지 보여 준다. 최초 관측·진단·재관측·후속 조치의 시간을 따라 설명한다.

실장비에서 확인한 항목, 기록 재생으로 확인한 항목, 남은 목표를 명시한다. 개인은 웹·데이터 관리, PC 앱, 실행·통신, 판정·재관측, 시험 중 맡은 범위의 코드·테스트·로그·분석 근거를 남긴다.

## 9. 첫 회의에서 합의할 일

1. 실제 관리자가 확인하는 장비·표시 상태와 현장 확인 업무를 정한다.
2. 이동과 촬영이 가능한 두 지점을 시험하고 첫 완결형의 범위를 정한다.
3. 작업 ID·관측·사진·확인 결과를 주고받을 형식을 합의한다.
4. 웹·PC 앱·작업/통신·로봇 연동·시험의 담당과 기간을 정한다.
5. 다섯 필수 영역을 갖춘 목표 완결형의 작업량을 산정하고, 자동 판정·ML의 착수 조건을 정한다.

실제 팀 인원·기간·분업·ROS2 배포판·평가 기준은 확인이 필요하다. 주행 안정성, 카메라 시야, 유효한 하드웨어 값, 고정 카메라 대비 효용, Docker 운영·연결 복구를 작은 시험으로 확인한다.

이 통합안은 사람의 사진 확인으로 첫 성과를 확보하고, 하나의 PC 앱에서 로봇 진단과 관측 자료 검토를 연결하는 구성을 제안한다. 자동 판정·보정·재촬영은 실제 실패 사례와 데이터를 바탕으로 확장한다. 주제와 구현 범위는 팀 회의에서 검토할 제안이다.
