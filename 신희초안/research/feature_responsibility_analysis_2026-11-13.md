### 공식 기록의 권한을 자료 종류별로 정하기

| 관리할 사실 | 최종 작성·관리 주체 | 연결이 끊겼을 때의 해석 |

**‘누구 기록이 항상 이긴다’보다 무엇을 확인한 기록인지가 중요하다.** 서버의 취소 의도와 그 전달 전 완료된 관측은 함께 존재할 수 있다. 이때 실제 발생한 관측을 보존하고 취소가 적용되기 전에 완료됐다는 처리 결과를 기록하는 정책을 제안한다. 정책 자체는 팀에서 합의한다.

업무 요청 상태, 실행 단계, 결과 전송 상태, 최종 확인 결과는 각기 의미가 다르다. 예를 들어 ‘촬영 완료·전송 대기·사람 확인 전’을 동시에 표현할 수 있어야 한다. 9번은 이 구분을 담당하고 1·2번 화면이 이를 조회하도록 구성한다.

### 필요한 최소 데이터와 인터페이스 계약

분석을 위한 후보 필드는 작업·항목·로봇 ID, 명령 ID와 실행 시도 ID, 관측·이벤트 ID, 작업 버전, 실행 프로그램의 부팅 ID·증가 순번, 원본 시각·수신 시각, 지원·유효 여부, 결과 이유·근거다. 모두를 첫 화면에 노출하거나 처음부터 별도 테이블로 만들 필요는 없다. 구현할 기능이 요구하는 필드부터 정한다.

서로 다른 PC의 monotonic 시간은 직접 비교하지 않는다. 갱신 간격은 같은 수집기의 시간으로 측정하고, 장치 시각과 수신 시각을 보존한다. 다중 호스트 시간축을 정밀 비교할 때는 시계 동기화·오차 범위를 추가로 검증한다. 수신 순번은 한 부팅 구간의 순서를 나타내며 전체 장치의 전역 시각을 대체하지 않는다.

| 연동 종류 | 인터페이스에 포함할 약속 | 검증할 결과 |
| --- | --- | --- |
| 작업 생성·취소 | 요청 식별, 내용·버전, 지원 기능, 수락·거부 이유 | 같은 요청 재전송과 서로 다른 의도의 새 요청을 구분 |
| 실행 명령·상태 조회 | 로봇·명령·시도 ID, 유효성·제어 주체, 접수·시작·확인 결과 | 연결 복구 후 무조건 다시 실행하는 동작 방지 |
| 실행 이벤트 보고 | 이벤트 ID·부팅 구간·순번, 관측된 단계·시각·근거 | 중복·순서 역전·이전 부팅 기록의 유실 없는 대조 |
| 관측 파일 업로드 | 관측 ID, 항목 연결, 파일 크기·해시, 수신 검증·확인 응답 | 부분 파일·메타데이터만 있는 상태를 완료로 처리하지 않음 |
| 기준·분석 결과 | 적용 자료·ROI·정답·기준 버전·작성자·실행 환경 | PC의 시험 기준과 실제 적용 기준을 재현 |

전송 방식은 HTTP·WebSocket·ROS2 등에서 팀 환경에 맞춰 선택한다. 위 약속은 전송 기술과 별개인 업무 의미다. 명령·결과·고속 영상·주기적 센서값은 처리량과 보존 필요가 달라 단일 메시지 정책을 무조건 적용하지 않는다.

### 복구 시 대조할 순서

1. 실행 프로그램이 재시작되면 로컬 명령·관측 기록과 실제 장치의 조회 가능 상태를 읽는다. 서버는 마지막 저장 업무·버전을 읽는다.
2. 완료한 관측·이벤트를 고유 ID로 전달하고 서버가 파일·메타데이터 저장을 검증해 확인한다. 관측 재전송은 같은 관측 ID를 사용한다.
3. 진행 중·취소 요청·실행 불명확 기록을 대조한다. 오래된 요청은 유효성·현재 작업 버전·제어 주체를 확인한 뒤 처리한다.
4. 기존 명령의 실행 여부가 불명확한 물리 동작은 확인 필요로 남긴다. 재실행은 원명령을 조회·정리한 뒤 명시적 새 시도로 처리하는 정책을 권한다.

파일 보존과 DB 반영 사이에도 중단이 발생할 수 있다. 임시 수신·검증·완료 구분과 정리 절차를 2·10번에서 함께 검토한다. 저장 용량이 부족하면 대기 자료를 조용히 버리는 대신 상태를 알리고 새 수집·보존 정책을 적용한다. 구체적인 용량·보존 기간은 팀이 정한다.

### 동일한 물리 동작의 중복 실행

요청 ID로 같은 요청을 식별하고, 수신 측이 내용까지 비교해 처리 상태·결과를 지속 저장하는 원칙을 제안한다. 동일 ID에 다른 내용을 보내면 충돌로 처리한다. 이 원칙은 AWS의 공식 재시도·멱등성 설명과 연결된다. [AWS 공식 기술 글](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

실행 프로그램은 같은 로봇에 대한 활성 명령 경로를 하나로 관리해야 한다. 웹·PC 시험·외부 도구 사이의 제어권과 버전을 확인하고 오래된 명령을 거부한다. 초기에는 실행 프로그램 하나와 운영·시험 모드 전환으로 검증할 수 있다. 복제 실행기·자동 인계가 필요해지면 이전 제어자를 실제 장치 경로에서 차단할 추가 설계가 필요하다.

| 중단 시점 | 남길 상태와 처리 제안 |
| --- | --- |
| 접수 기록 전 | 실제 동작 전에 접수·의도를 지속 기록하는 순서를 정한다. 동일 요청 재수신 시 식별한다. |
| 시작 의도 기록 후 실제 동작 전 | 재시작만으로 실제 실행 여부를 단정하기 어렵다. 장치 조회가 불가능하면 확인 필요로 둔다. |
| 실제 동작 후 결과 기록 전 | 모형 투척 등 되돌릴 수 없는 동작은 특히 불명확하다. 자동 반복 대신 관측·사람 확인을 거친다. |
| 결과 기록 후 응답 유실 | 같은 명령 ID 조회·재수신에 저장 결과를 반환하고 물리 동작을 반복하지 않는다. |

**DB 트랜잭션과 물리 동작을 하나의 원자적 처리로 묶을 수 있다는 근거는 현재 없다.** 장치 자체가 명령 ID·실행 이력을 제공하는지에 따라 보장 범위가 달라진다. HTTP 성공·ROS 발행·서보 각도 명령을 실제 투척·명중 확인과 구분한다. Nav2의 취소 인터페이스도 사용 가능 여부와 응답·실제 정지 의미를 설치 환경에서 확인한다. [Nav2 Humble 소스](https://api.nav2.org/nav2-humble/html/robot__navigator_8py_source.html)

로컬 README의 ‘엔코더가 없으므로 위치 추정은 카메라 기반으로 해야 한다’는 문장은 설계를 제한하는 근거로 사용하기 어렵다. 엔코더 부재는 해당 휠 측정이 없다는 뜻이며, 위치 추정 방법의 채택은 가능한 센서·외부 기준·임무 요구에 따라 검토한다. 이 분석은 원본 README의 문장을 수정하지 않고 해석 범위를 명시한다.

### 서로 다른 통신·제어 방식을 연결하는 후보

| 구성 후보 | 연결 방법·장점 | 비용·위험 | 선택 조건 |
| --- | --- | --- | --- |
| 두 로봇의 ROS2 인터페이스 통일 | 각 로봇의 검증된 드라이버·노드를 ROS2에서 제공하고 공통 실행 프로그램이 이용한다. | JetBot 드라이버·OS·SDK 이식과 유지보수 부담. ROS2 노드 하나로 동일 자율주행 능력이 생기지는 않는다. | 현재 이미지에서 ROS2 지원이 검증되거나 이식이 팀 목표에 부합할 때 |

ROS1 bridge 공식 저장소는 양쪽 ROS 환경과 빌드·메시지 대응 조건을 설명하고 Ubuntu별 제약을 제시한다. 따라서 ‘브리지 설치만 하면 연결 완료’라는 전제는 채택하지 않는다. [ros1_bridge 공식 문서](https://github.com/ros2/ros1_bridge)

**분석자 제안은 16번에서 현재 환경을 확인한 다음 세 후보를 비교하는 것이다.** 혼합 어댑터는 이식 범위를 줄일 가능성이 있지만, 실제 SDK·완료 응답·중단 방법을 확인해야 가치가 판단된다. 두 로봇에 공통으로 요구할 항목과 각각 지원하는 항목을 나눠 표현하고 특정 임무는 배정하지 않는다.

| 실행 프로그램 위치 | 서버 PC 중단 시 영향 | 검토할 조건 |
| --- | --- | --- |
| 백엔드와 같은 PC | 백엔드·실행·전송 대기가 함께 멈출 수 있다. | 구성이 간단하지만 PC 전체 장애 중 동작·기록 지속을 약속할 수 없다. 별도 로봇 제어기의 진행 상태도 확인한다. |
| 각 로봇 또는 별도 생존 PC | 서버가 꺼져도 로컬 프로그램·저장이 살아 있을 수 있다. | CPU·저장 공간·권한, 통신 단절 시 허용 동작과 중단 정책, 재접속 대조가 필요하다. |

단절 중 현재 작업 계속·정지·관측 보관 중 무엇을 허용할지는 작업별 팀 정책이다. 새 서버 요청이 없는 동안 이전 캐시에서 임의로 새 임무를 만드는 동작은 기본 복구 정책에 넣지 않는 구성을 제안한다.

## Compose 기능과 애플리케이션 복구의 경계

| 상황 | Compose·Engine이 제공하는 부분 | 직접 구현·검증할 부분 |
| --- | --- | --- |
| 앱이 DB보다 먼저 시작 | depends_on·healthcheck·service_healthy 같은 시작 조건 | 실제 쿼리 가능 상태 확인, 실행 중 DB 단절·재연결, 요청 처리 실패 정책 |
| 컨테이너 프로세스 종료 | 설정한 restart 정책에 따른 재시작 | 마지막 작업 조회·상태 대조·중복 방지·파일 정리·실행 재개 판단 |
| 프로세스가 살아 있지만 업무 불가 | healthcheck가 검사 결과를 상태로 제공 | 업무 준비 검사와 대응 정책. unhealthy 표시만으로 자동 재시작·업무 복구가 된다고 해석하지 않는다. |
| 컨테이너 재생성 | 설정한 볼륨에 파일·DB 데이터 보존 | DB와 사진 저장소 모두의 경로·완료 일관성·보존·복구 시험 |
| 서버 PC 전원·OS 중단 | 같은 PC의 Engine도 중단. PC 복구 후에는 환경·정책에 따른 기동 가능. | 다른 생존 위치의 실행·로컬 기록, 단절 중 정책, 부팅 후 대조. 전체 장애 중 지속성을 실행 위치별로 평가한다. |
| 서버 PC 디스크 손실 | 동일 디스크의 로컬 볼륨은 함께 영향을 받을 수 있다. | 별도 백업·복원 범위를 합의하고 시험한다. 자동 이중화는 현재 필수 범위로 추가하지 않는다. |

공식 문서는 시작 순서·준비 조건, 컨테이너 재시작 정책, 호스트에 저장되는 볼륨을 각각 설명한다. 여기서 업무 재시작·로봇 기록의 복구를 자동 제공한다고 해석할 근거는 없다. [시작 조건](https://docs.docker.com/compose/how-tos/startup-order/) · [재시작 정책](https://docs.docker.com/engine/containers/start-containers-automatically/) · [볼륨](https://docs.docker.com/engine/storage/volumes/)

24번 시험은 서버 API 응답 유실, 서버 컨테이너 종료, DB 준비 지연, 실행 프로그램 종료, 서버 PC 전체 중단을 서로 다른 시나리오로 기록한다. 컨테이너 종료만 시험하고 ‘서버 PC 장애에도 지속’이라고 보고하지 않는다. 첫 범위는 합의한 한 장애와 정상 업무의 자료 대조까지로 제안한다.

아래 단계는 팀이 검토할 후보 순서다. 준비 활동과 사용자에게 끝난 업무를 구분하고, 새 기능은 정상 흐름과 실패 시험을 함께 완료한다. 시간·인원별 일정은 산정하지 않았다.

| 개발 후보 | 범위와 선행 조건 | 완료 기준·검증 | 이 단계에서 남는 성과 |

| 채택 시 모형 투척 | 20 수동 기록→21 결과 검토→22 실제 보정. 기구·영상·명령 확인이 선행한다. | 투척 조건·명중 근거·불확실 결과를 기록하고 보정 전후를 같은 조건에서 비교한다. | 초기에도 시험·결과 분석이 남고, 자동 보정은 도전 단계로 확장 |

두 로봇 참여의 완료 기준은 정상 세팅 후 팀이 임무를 정해야 확정된다. 이 문서에서는 역할을 배정하지 않았다. 세팅 조사·상태 표시만으로 유의미한 최종 참여를 달성했다고 평가하지 않는다.

실장비 실행을 기다리는 동안 PC 자료 분석·보정·시험 형식을 개발할 수 있다. 이때 모의·고정 자료의 성과를 따로 표시하고 실제 관측 업무와 연결해 다음 완료 기준을 확인한다.

| 필수 입력·기준 | 배터리·카메라·센서 중 작업에 무엇이 필요하고 미지원은 어떻게 처리할까. | 실제 값의 의미·주기·검사 결과, 5·14·16번 |

| 기간·인원·담당·기술 | 모듈의 책임자와 맞닿는 인터페이스, 우선 완료 단위, 언어·프레임워크·배포 방식 | 팀원의 경험·직무 관심·실험 환경·통합 시험 여력 |

첫 회의에서는 사용자와 최소 업무, 두 로봇 세팅 확인 담당, 웹·PC의 독립 목적, 장애 시험 한 종류를 우선 정하면 나머지 결정의 근거가 생긴다. 특정 로봇에 점검·신고·투척 임무를 미리 고정하는 결론은 이 문서에 포함하지 않았다.

## 개인이 우선 탐구할 기능의 비교 평가

대화에서 확인한 개인 희망은 여러 소프트웨어 영역을 직접 개발하고 싶다는 의향이다. 아래 우선순위는 분석자의 제안이며, 실제 숙련도와 개인 선택을 확정한 평가가 아니다. 점수·기간 대신 의존성과 남길 결과를 비교한다.

| 개인 탐구 후보 | 직접 책임질 수 있는 결과 | 시작 의존성·부담 | 직무와의 연결·주요 한계 | 검토 순서 제안 |
| --- | --- | --- | --- | --- |
| 작업별 PC 조사·내보내기 / 6·7, 5·15 일부 | 실제 실패 근거를 찾아 분석 의견·자료 묶음을 제공 | 작업 자료 형식과 제한된 수집. 범용 시간축·대용량 재생 확장은 부담이 크다. | PC 응용·장치 연동·시험 분석. 그래프만 구현하면 Foxglove 중복이 크다. | 첫 탐구 후보. 한 사건의 조회·조사 완료부터 시험한다. |
| 사진 보정·평가 / 17·18·19, 8 일부 | 같은 자료에서 기준·오판·재촬영 필요를 비교 | 사진·라벨 확보. 고정 자료로 독립 시작 가능. | OpenCV·알고리즘·응용 SW. 새 촬영 조건으로의 일반화 검증이 남는다. | 첫 탐구 후보. 사용자가 비교적 시도할 만하다고 표현한 영역과 연결된다. |
| 복구 가능한 결과 전달 / 9·10·11, 24 일부 | 정한 장애에서 저장·재전송·중복·불명확 실행을 검증 | 백엔드·실행 담당과 계약 필요. 지속 저장·동시성의 부담이 높다. | 백엔드·통신·시스템·QA. 선택 언어와 실제 구현 깊이를 증명해야 한다. | 공동 책임 경계를 합의한 뒤 작은 장애 한 종류로 탐구한다. |
| 로봇 상태·준비 검사 / 5·14·16, 15 일부 | 실제 입력을 작업 판단·조사 근거로 사용 | 장비 접근과 상태 의미 검증이 필요하다. | 하드웨어 연동 응용·시험. 상태 표시·조사만으로 펌웨어 구현을 증명하지 않는다. | 실장비 확인이 가능할 때 병행할 기반. 단독 최종 산출물은 준비 검사 업무까지 완결한다. |
| Docker·장애 시험 / 23·24 | 팀원 환경 재현, 재시작 후 기록·동작 검증 보고 | 실행할 업무 서비스가 있어야 효과를 검증할 수 있다. | 운영·인프라·자동 시험. Compose 파일만으로 업무 복구를 증명하기 어렵다. | 개인의 강한 활용 의향을 반영해 다른 담당 모듈과 함께 책임질 후보 |
| 모형 투척 시험 도구 / 20·21, 이후 22 | 기구 조건·명중 근거·오차·보정 효과 보고 | 수동 기록은 작게 가능. 실제 기구·관측·제어 통합은 의존성이 높다. | 장치 시험·계측 응용·비전. 자동 보정까지 필수화하면 첫 완성이 멀어진다. | 팀 채택·기구 시험 이후 확장 후보 |

**첫 개인 탐구로는 PC 작업 조사 또는 사진 보정·평가 중 하나를 고르고, Docker 운영·검증을 해당 모듈과 연결하는 방향을 권한다.** 통신 복구를 우선하고 싶다면 백엔드 수신 책임과 실행 측 저장 책임을 먼저 합의해 작은 장애에서 끝나는 기능을 정한다. 여러 묶음을 동시에 개인 담당으로 확정할 필요는 없다.

기존 수집 공고와의 업무 연결은 원본 문서의 비교를 참고할 수 있다. 이번 문서는 지원 자격이나 현재 채용 상태를 재평가하지 않았으며, 개인 탐구 우선순위는 직무 이름의 유사성보다 실제 구현·검증 범위로 판단했다. [원본의 공고 연결 분석](feature_exploration_2026-11-13.html#jobs)
